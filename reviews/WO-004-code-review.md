## Attack results

1. **`onPause` order and `onStop`.** `MainActivity.onPause` runs `host.session?.interruptDrag()` then `controller.persist()` then `super.onPause()`; `persist` itself calls `host.capture`, which calls `toProgress`, which calls `interruptDrag()` again (idempotent). So even if a caller skipped the first line, no `Dragged` state could be stored. `onStop` calls `store.sync()`, which never throws (CR-2). A rotation runs the same path and the store skips an equal write. Order is as designed. Only `onPause` before `model` is assigned would crash (`lateinit`), which needs `onCreate` to have thrown first; not a touch or stored-data path. Clean; the missing test is F3.
2. **`onChanged` to `persist` wiring.** `settled()` is called after the intent is complete (PlaySession.kt:242, 250, 277, 331: the drag is already cleared). `persist()` then calls `capture`, `toProgress`, `interruptDrag()`: no drag, so no mutation, and no further `onChanged` (`toProgress` and `restore` never call it, PlaySession.kt:354, 369). No recursion. `SessionHost.show` builds the session and calls `restore` (silent) before `session` is assigned, so there is no persist during `show`. The one overlap I could construct: a tray tap and a › press by two fingers in the same frame. `open` swaps the session first; the old session's queued `Up` then fires the old `onChanged`, which persists the *new* session under the *new* index. Harmless (an equal write, skipped). Clean.
3. **ViewModel across rotation, process death, Back.** `AppViewModel` holds library, store, host and controller; `gridOpen` and the session survive recreation; `onCreate` interrupts a drag again; the clock seed from `lastFrameMs` (WO-003 CR F1) still applies to the kept session. Process death: a new ViewModel reads the file, `start()` goes to `lastShown` (written by `open`), else index 0, and `show` restores through the same `showAt` path. `BackHandler(enabled = controller.gridOpen)` is read in composition, so it follows the flag; with the grid closed Back leaves the app and `onPause` persists. An open grid is not restored after process death (designed). Clean.
4. **DA-54 long press.** `combinedClickable(onClick, onLongClick)` inside `CompositionLocalProvider(LocalViewConfiguration provides …)`; the delegate overrides only `longPressTimeoutMillis = max(500, platform)` and is `remember(platform)`-keyed. `Layout` writes `LocalViewConfiguration` into the layout node, which is where the gesture reads it. `nextUnsolved()` is guarded by `isDragging` and falls back to `next()` (DA-54). A hold fires once; the release after a long click is not a click. The dependence on the platform default (400 ms on current Android, so 500 applies) is as the design states. Clean for mechanics; the visible test cannot tell a long press from a tap (N2).
5. **Thumbnail cost.** `PuzzleThumbnail` computes `forThumbnail` and the union in `remember(puzzle, w, h)`, draws the vector picture into the cell's own display list, reads no state, runs no frame loop and does not touch the `silhouettePath` slot (it calls `buildSilhouettePath`). A `LazyVerticalGrid` composes only the visible cells; at 360 dp that is three columns, so the first open composes up to about 13 cells once: 13 unions of at most seven polygons. Not measured; the arithmetic is small. `stateOf(i)` reads the store map (not snapshot state) for the other cells and `host.state` for the shown one, and the grid cannot open during a drag (guard), so the grid itself does not recompose per frame. The per-frame recomposition that does exist is F2.
6. **G-10 from touch and stored data.** `SessionHost.show` wraps build and restore in `runCatching`; `sanitize` is fail-closed per piece (CR-2); `stateOf` and `shownBestSeconds` read a map that never throws; `ProgressRestore` input comes from the reader's bounds. `SolvedBar` formats `(bestSeconds / 60).toInt()`: a huge stored `Long` gives a wrong number, not a crash (carried to WO-008, N6). `open`, `restart` and `openGrid` are guarded against a drag. An unreachable crash remains in `check(puzzles.isNotEmpty())` (DA-57, accepted). What the fallback does when it is reached is F4.
7. **Back with the grid open, grid swallowing touches.** The overlay sits last in the root `Box`, with a `pointerInput(Unit) { detectTapGestures { } }`; the top bar, board, Restart pill and solved bar are covered. Cells use a sibling click layer so the dot stays findable. Clean.
8. **Solved region.** The `solvedBar` slot is a sibling above the gesture box, positioned at `layout.trayTop` through the bottom, so the tray, marks, badge and outlines are gone (`trayShown`, `visibleSizeMarks`, `badgeRect`, `trayCellsPx` all key on SOLVED; DA-52/69). The empty part of the slot's box is not a pointer node, so a tap there falls to the gesture box, where every SOLVED path is a no-op (`beginDrag`, `tapTray`, `boardPiece` all return when SOLVED). A restored solved session has `t0 = -10 000` and seeds the clock from 0, so `sinceSolve` is 10 s from the first frame: settled. Clean.

## Findings

### F1 — OVERLAP / SAFETY · Should · app/TangramApp.kt:63-65 (with browse/SolvedBar.kt:89-112, play/PlayLayout.kt:178-179) · owner TASK-028 (placement) with TASK-026 (layout), brief for TASK-027
- **Observation:** the Restart pill is a sibling over the whole play area, aligned `TopStart`, with a touch area of at least 48 x 48 dp and a drawn width of about 84 dp (en) or 124 dp (fi). The board rect starts at (0, 0) and the silhouette is only inset by `BOARD_W_FRACTION` 0.82 and `BOARD_H_FRACTION` 0.80, so the pill has no reserved space. Measured with the real layout formulas (see Evidence): on 360 x 780 and 390 x 844 phones with three-button navigation, `shapes-warmup-1` (the first warm-up, every new player passes it) has a silhouette corner under the pill (8 to 26 dp squared), `shapes-square` joins at larger insets, and on a 360 x 640 window `shapes-warmup-1` and `shapes-square` lose 208 to 985 dp squared. The pill is drawn above the board (so it hides that part of the target) and it takes the touch before the board does: tapping a locked piece in that corner, or starting a drag of it, presses Restart. `BrowseController.restart()` runs at once, with no confirmation, and returns every piece to the tray (REQ-025 A2). The player is 8+ and the pill appears exactly while there is progress to lose. The DA-70 playtest note records the position as Spec/02's; it did not measure the overlap.
- **REQ/decision:** REQ-025 rule 2 and A2 (Restart is deliberate); REQ-037 A1 (a control that steals a neighbour's touch area); Spec/02 line 56; DA-53, DA-70.
- **Proposed resolution:** keep the pill but stop it overlapping what it hides. Cheapest and layout-independent: in `TangramApp` pick `TopStart` or `TopEnd` per puzzle with a pure function `pillSide(layout, puzzle)` that returns the side whose 48 x pillWidth box misses every silhouette polygon (play exposes the polygons through `PlayLayout.silhouetteDp`; `app` cannot see `internal`, so add a small `internal` helper in `play` or pass the rectangle). Alternative: reserve a 48 dp strip at the top of `boardRect` while Restart is shown (changes `fitSilhouette` height by 48 dp, which also moves REQ-011 numbers, so spot-check). Whichever is chosen, add a JVM test that sweeps the 13 puzzles over 360 x 640, 360 x 780 and 390 x 844 with insets 0, 48 and 96 and asserts zero overlap; the Python port in the scratchpad is a starting oracle. Also consider a one-line confirm or an undo for Restart (not asked by any REQ, so a recorded decision rather than a defect) and `maxLines = 1` with an ellipsis on the pill text, which has none (a font scale above 1.3 widens the pill and the overlap).

### F2 — PERFORMANCE · Should · play/PlaySession.kt:120-127, 206, 221 with app/TangramApp.kt:63 and browse/BrowseTopBar.kt:54 · owner TASK-028 and TASK-027 (call sites), TASK-024 (the source)
- **Observation:** `PlaySession.state` and `isDragging` are "observable" by reading `versionState`, and `versionState` is bumped by every `invalidate()`, including `dragTo` (PlaySession.kt:204-207) and every drag `onFrame` (:221). `controller.shownState` is `host.state` is `session.state`, and it is read directly in the body of `TangramApp` (the Restart condition, :63) and of `BrowseTopBar` (:54). Both composables therefore recompose on every drag frame. `PlayArea` avoided exactly this with `derivedStateOf { session.state == SOLVED }` (PlayArea.kt:85, DA-52: "only a change of the answer recomposes"), but the two new readers did not. `PlayArea` already recomposes per frame (WO-003 CR N3, accepted), so this adds a second and a third scope to each frame; with strong skipping the children are skipped, but the top bar's text and rating dots are re-evaluated. Not measured; it is likely sub-millisecond on a fast phone and visible on a slow one during the drag, which is the feel-critical interaction (REQ-014).
- **REQ/decision:** DA-52, WO-003 CR N3, design section 4 ("now observable").
- **Proposed resolution:** the cleanest fix is in the source: back `state` with its own `mutableStateOf` written only when the value changes (and `isDragging` the same), so an unchanged answer never invalidates a reader; `drawPlay` keeps using `version`. Or at the call sites: `val inProgress by remember(controller) { derivedStateOf { controller.shownState == IN_PROGRESS } }` in `TangramApp`, and the same for the state text in `BrowseTopBar`. Add a device scaffolding test that counts recompositions of a probe reading `host.state` during a 30-frame drag and asserts at most one.

### F4 — G-10 / DATA PRESERVATION · Should · app/SessionHost.kt:29-33 (with browse/BrowseController.kt:46-50, 107-111) · owner TASK-028
- **Observation:** the fallback chain is `restored ?: newSession ?: session`. Two defects in what it does when it is reached. (a) If restoring fails, a New session is shown and nothing records that the stored entry was not shown; the next `persist` (any tray tap, ›, `onPause`) writes the canonical New form over the stored In-progress entry, so a restore bug silently destroys the saved puzzle, the exact REQ-025 harm, and G-09 says the old document is not to be lost. (b) If building the New session also fails, `session` stays the *previous puzzle's* session while `BrowseController.showAt` has already set `indexState = i` (BrowseController.kt:47, before `host.show`); `persist()` then captures that old session and stores its pieces under the *new* puzzle's id. Both paths are unreachable today (the constructor is total on a validated puzzle and `sanitize` is fail-closed), so this is defensive code that does the wrong thing if it is ever needed. Nothing logs the swallowed exception, so a field failure leaves no trace.
- **REQ/decision:** REQ-025, G-10, G-09 spirit, CR-2 F9.
- **Proposed resolution:** keep "never throws", but (a) on a restore failure log it and leave a flag the controller can read (or have `show` return a Boolean) so `persist` skips the write for that puzzle until the player's first real event, or make `capture` return null while the shown session is a fallback; (b) make `capture` return null when `session.puzzle.id` differs from the id `persist` is saving (pass the id, or compare in `BrowseController.persist` through `host.shownPuzzleId`); (c) one `Log.w` line in each `runCatching` (G-01 allows local logging). Test with F3(a).
