# Design — WO-008 · #PlayTime: active play time, solve times, best times and the timer

**Author:** Design Author  ·  **Date:** 2026-10-04  ·  **Rev 0**  ·  **Baseline:** architecture.md v1.0 (G-01, G-04, G-05, G-06, G-07, G-09, G-10, O-04, O-06, O-08, O-09, §3, §5, ADR-005), build-map v1.6, decisions.md (to DA-132; F4, F5, F14, F28, DEF-001, DA-26…DA-71, DA-73/77, DA-88/89, DA-92, DA-113…DA-132), governance rows 11, 12, 14, REQ-005, 029, 030, 031, TYPE-005, TYPE-006 and the carried REQ-001, 008, 010, 032, 034, 037, 046, `Spec/01-gameplay.md` §8, `Spec/02-ui-layout.md`, `designs/WO-004-design.md`, `designs/WO-007-design.md`, and the code as it stands today (`contracts`, `store`, `play`, `browse`, `settings`, `app`, `kernel`).

**In one paragraph.** Time is counted from **timestamps, not ticks**: a small pure rule in `kernel` (TYPE-005) credits the part of each interval that was visible and within 60 s of a touch, and a new `time` module owns the accumulator (`PlayTimeKeeper`), fed by a **monotonic, injectable `TimeSource`** (tests never wait). Puzzle time counts only while an In-progress puzzle is shown with no settings or grid on top; today and total count whenever the second is active. **Everything fits the frozen v1 format** (`puzzleSeconds`, `bestSeconds`, `playTime`, `settings.timerShown`): no field, no migration, no contract edit. The keeper's seconds reach the store through the **existing persist path** (a one-line merge in `SessionHost.capture`) plus a **10 s flush** that never creates a record or changes a state, so a Restart, a Retry, a leave or a reset can never be overwritten by a stale value. The settings screen gets the timer row first and a play-time section after sound (REQ-032's order) through a one-method readout seam, and the on-board timer is an inert pill in the board's top-right corner, which the Restart and DEV controls learn to leave free.

## Chosen design

### 0. Shape in one picture

```
kernel : ActiveSecond (TYPE-005 rule: activeMs, puzzleCounts)  ·  DurationFormat.parts (one time format)       pure, JVM
time   : TimeSource ── PlayTimeKeeper(source, store, onCountingChanged)  ·  PuzzleTimer (composable, inert)
play   : PlaySession.solvedListener(byAid) · PlayArea(timer slot) · computeWithCorner/placeSecondary(reserveTopRight)

app    : AppViewModel { time, ticker } · SessionHost.time (show -> puzzleShown, capture -> mergeInto, solve -> solved)
         TangramContent { root touch observer, snapshotFlow(running), timer slot, readout }  MainActivity { onStart/onStop/onPause }
inputs to the keeper:
  touch(pressed)  <- root Compose pointer observer, Initial pass, never consumes
  setVisible      <- Activity onStart / onStop
  setPuzzleRunning<- snapshotFlow { puzzleCounts(host.state, settings.isOpen, controller.gridOpen) }
  puzzleShown     <- SessionHost.show (every show: start, open, restart, retry, afterReset)
  solved(byAid)   <- PlaySession.solvedListener
  afterReset      <- SettingsController.onReset (after controller.afterReset)
```

### 1. Module shape (G-06) *(item 6)*

**`time` is confirmed as the code home** (`build-map.md` §1), a new Android library: `include(":time")`, `time/build.gradle.kts` a copy of `settings`' (android-library + compose plugin, `implementation` of `:kernel`, `:contracts`, the BOM and `compose.foundation`; test scope as `settings`, no `:store`, no `:content`). **Main scope: `kernel` + `contracts` only**, exactly V-06's `time: {kernel, contracts}`; only `app` depends on it, so no cycle is possible. No manifest. Namespace `io.github.jamisuni.tangram.time`.

**The split inside:**
- **`kernel` owns the TYPE rules** (architecture §3 lists "TYPE-005 active-second rule" under `kernel`; D1: implemented once): `ActiveSecond` (the 60 s rule and "which screens let the puzzle count") and `DurationFormat.parts` (the m:ss / h min split, used by `browse`, `settings` and `time`, which each hold the two format strings). Pure, JVM-tested.
- **`time` owns counting** (O-04): `PlayTimeKeeper`, `TimeSource`, and `PuzzleTimer`, the on-board timer composable. No Android type in the keeper (a plain Kotlin class with Compose snapshot state for observation, as `PlaySession` does), so its tests are JVM.
- **`settings` does not depend on `time`** and `time` does not depend on `settings` (G-06). The settings screen reads today and total through a **one-interface seam** it owns (`PlayTimeReadout`), implemented in `app` over the keeper; the best-time list reads the store and the library it is handed (section 6).

**Why not no new module:** `time` is named by `architecture.md` §3, O-04, O-06, O-08 and `build-map.md` §1, and trace-check rule 3 wants REQ-005/029/030/031's covering tests under the code home. **Why not everything in `kernel`:** the keeper holds snapshot state and a composable belongs next to it; `kernel` is JVM-only.

### 2. The time model (TYPE-005, the active second) *(item 1)*

**2.1 What is active: `ActiveSecond.activeMs(prevMs, nowMs, visible, lastTouchMs, touching)`.** Of the interval (`prevMs`, `nowMs`] it returns the milliseconds that were **visible and within 60 s of a touch**:

```
if (!visible || nowMs <= prevMs) 0
else if (touching) nowMs - prevMs                     // a finger is down: engaged
else if (lastTouchMs == null) 0                       // never touched since the process started
else max(0, min(nowMs, lastTouchMs + 60_000) - max(prevMs, lastTouchMs))
```
`IDLE_LIMIT_MS = 60_000` is TYPE-005's locked ASSUMPTION, a single constant. The window is inclusive ("at most 60 s ago"), so 5 minutes untouched credits exactly 60 s (REQ-029 A1: "at most 60 s").

- **"Visible":** the Activity is **started** (`onStart` … `onStop`), the Android meaning of "on screen". Not a frame or composition test: an idle board schedules no frames (WO-003). The keeper never learns of frames.
- **"Touch":** a pointer **contact**: any pointer event in which a pointer is pressed or was pressed (down, move, up, cancel), observed at the app root (section 5.3). Hover, a mouse move without a button and a key press are not touches. **A finger held down counts as engaged** (`touching`): a child holding a piece while thinking is playing; the flag is cleared on the up, on cancel and when the app stops being visible.
- **Interval accrual, not tick counting** (the prototype adds 1 per `setInterval` second). Each input first closes the open interval under the **old** flags (`accrue`), then changes the flag. Consequences: a late or dropped tick, a GC pause, a main-thread stall and a device sleep neither lose nor invent time (a sleep is bounded by the 60 s window, and `System.nanoTime` does not advance in deep sleep); one jump of 5 minutes in a test credits exactly what 300 one-second steps credit.
- **Sub-second remainders** are carried in memory (`puzzleCarryMs`, `playCarryMs`) and only whole seconds are committed, so nothing is rounded up (A1's "at most 60 s" holds to the millisecond) and a restart loses under 1 s.

**2.2 What pauses what.**

| Situation | Puzzle time | Today and total |
|---|---|---|
| Visible, touched within 60 s, an **In-progress** puzzle shown, no overlay | counts | counts |
| New puzzle shown (a tray tap or turn, REQ-030 A3) | **no** | counts |
| Solved puzzle shown | no | counts |
| All-puzzles grid open (REQ-050) | no (F28: grid pauses) | counts |
| Settings open (`isOpen`, REQ-032) | no | counts while the player touches it |
| Browsing to another puzzle (‹ ›, grid) | the shown puzzle's own seconds, adopted from the store | counts |
| Backgrounded, screen off, rotation gap (about 100 ms) | no | no |
| Untouched for more than 60 s | no | no |
| Finger held down | counts | counts |
| Process death or crash | resumes from the last save (section 4.3); **not counting until the first touch** | same |

The puzzle clock's gate is a pure rule in `kernel`: `ActiveSecond.puzzleCounts(state, settingsOpen, gridOpen) = state == IN_PROGRESS && !settingsOpen && !gridOpen` (TYPE-006: "time is counted only In progress"). **When a puzzle's time starts (REQ-030 A3):** exactly when TYPE-006 moves New to In progress, a drag starting on a tray piece (`PuzzleStates.onTrayDragStarted`); tapping or turning a tray piece leaves it New, so it starts nothing. The time **stays** In progress when the piece is sent home (the empty In-progress board, TYPE-006): the clock keeps running, as the state says.

**2.3 The idle cut-off against a child who thinks for a long time.** TYPE-005 is locked at 60 s; a player who studies a puzzle for two minutes without touching it is not counted for the second minute. This is the locked rule, not a build choice; it is the **owner-playtest item** for the constant (risk list). A held finger is the one softening, and it is mine (DA-134).

**2.4 The clock: an injectable `TimeSource`** (WO-003's precedent, "time is handed in, never read ambiently", E5):

```
interface TimeSource { fun nowMs(): Long  /* monotonic */ ; fun today(): java.time.LocalDate /* local date */ }
object SystemTimeSource : TimeSource       // System.nanoTime() / 1_000_000 ; LocalDate.now()
```
`System.nanoTime` is monotonic, immune to wall-clock and time-zone changes, JVM-callable (no Android type, so the keeper's unit tests need no mocking) and stops in deep sleep. The frame clock is not usable (no frames when idle), `SystemClock.elapsedRealtime` would count sleep. Tests use a `ManualTimeSource` (a fake each test kit owns). **Device tests** swap it through a debug-only seam (section 5.5), so **nothing ever sleeps**: a device test advances the manual clock by minutes and calls the public `keeper.accrue()` on the main thread.

### 3. Solve time, best time, attempt time, reset *(item 2)*

- **When the solve time is fixed:** at the **solve event** (`PlaySession`'s completing drop, inside `release()`, before the 2.4 s timeline). `keeper.solved(byAid)` first accrues the open interval, then freezes `puzzleSeconds` and stops the puzzle clock.
- **Where "its solve time is available" (REQ-005 A1) lives:** in the existing field, `puzzleSeconds` of the **Solved** record, written by the same persist that writes the state (section 5.1). It stays until Retry (`restarted()` resets it to 0). On a first solve the best equals it, and the solved bar shows it; the settings list shows every best. This is a reading (DA-136, CA-10): REQ-026 asks for "the best time", not a separate solve-time line, so no extra element is added (D4).
- **Best time:** on a player's own solve, `best = min(best ?: Long.MAX, puzzleSeconds)`; a slower re-solve keeps the earlier time (REQ-030 A2); equal keeps. A best of `0` is a legal value and differs from `null` (shown `–`).
- **An aid solve never sets a best** (REQ-030 rule 4, REQ-046 A3, the carried WO-005 regression): `solved(byAid = true)` freezes the seconds counted so far (the Solved record then holds them) and leaves the best alone. It amends DA-77 ("`puzzleSeconds` untouched") to "the seconds counted so far", which is what the store would hold a moment later anyway; "Solved with a null best" still means "by the aid, or solved before time existed".
- **Retry and Restart:** `BrowseController.restart()` writes `progress.restarted()` (seconds 0, best kept) and shows the puzzle; `show` calls `keeper.puzzleShown(id, progress)`, which **adopts** the stored 0 and the stored best. The next attempt counts from 0 (REQ-030 rule 2).
- **Reset (REQ-034, DA-120: settings are kept):** the store erases puzzles, bests and play time and keeps `settings` (including `timerShown`) and `lastShown`. `SettingsController.onReset` becomes `{ controller.afterReset(); time.afterReset() }`: `afterReset()` re-reads the (erased) play time into memory, drops the carries and does **not** write. The shown puzzle's seconds and best come back as 0 and `null` through `show`'s `puzzleShown`. This is the "reload `time`" that O-08 and DA-120 reserved.

### 4. Persistence against the frozen v1 format, and the row-11 analysis *(item 5)*

**4.3 When and how often to save, and the loss bounds (ADR-005, O-08)**

The keeper holds the live seconds in memory; the store receives them by three routes, all main thread, all an atomic whole-document write (`JsonProgressStore` skips an equal save):

1. **On every settled puzzle event, on leaving a puzzle and on `onPause`:** `SessionHost.capture` merges the keeper's seconds and best into the captured progress (`mergeInto`), so they ride the **one** write `BrowseController.persist` already makes. This also covers `open()`'s "save the leaving puzzle" and `onPause`'s persist, and means the time and the board are saved together (one write, not two).
2. **`keeper.flush()`** writes `store.savePlayTime(PlayTime(day, today, total))` and, for the shown puzzle, a read-modify-write of `puzzleSeconds` **only when the stored record is In progress and the value differs**. It never creates a record, never changes `state` or `pieces`, never writes a best, and never touches the board, so it is safe in the middle of a drag (it does not go through `toProgress`, which would interrupt the drag). When: every **10 s** of source time while counting; when counting stops (idle expiry or background); when the puzzle clock stops; `onPause`; `onStop` (before `store.sync()`).
3. The solve is saved by route 1 (the completing event's `settled()` runs right after `onSolved`).

| Event | Loss |
|---|---|
| Normal exit, home button, screen off, swipe from recents, a system kill while backgrounded (always after `onStop`) | **0** |
| A puzzle event (lock, return, turn, solve) then a crash | the seconds since that event, **at most 10 s** |
| A crash, force-stop or battery pull while playing | **at most 10 s** of puzzle, today and total, plus under 1 s of carry |
| A power cut without `onStop` | as above, plus whatever the OS has not flushed (the existing store behaviour, ADR-005) |

**Disk churn:** at most one small write per 10 s while counting, none while idle, plus the writes the board events already make. No write per second. **Battery:** no polling when idle (section 5.4).

**4.4 One reading against O-08 (logged, DA-137).** O-08 says "no slice keeps a stored record across events" and assigns `time` the writes of `puzzleSeconds`, `bestSeconds` and the play time. The keeper does keep **counters** between events (a record per second would be a write per second). It is the sole writer of the play time, writes whole values from counters it owns, and the "reload after reset" clause of O-08 is `afterReset()`. For the puzzle fields the store stays the source for every other field (the flush and the merge are read-modify-writes), so `state`, `pieces` and `settings` are never overwritten with a stale copy.

### 5. Wiring and ownership of the seconds *(items 1, 2, 6)*

**5.1 One owner, ordered writes (the highest-risk part).** While a puzzle is shown, the keeper's memory is authoritative for exactly two fields of its record, `puzzleSeconds` and `bestSeconds`; `BrowseController` is authoritative for `state` and `pieces`. The four things that can write those two fields, and why none can resurrect a stale value:

| Writer | Order guarantee |
|---|---|
| `SessionHost.capture` -> `mergeInto(id, captured)` | applies **only when `id` is the keeper's current puzzle**; first accrues (so a leave loses no second); a `NEW` captured state forces 0; the result is written by `persist`'s one `saveProgress` |
| `keeper.flush()` | a read-modify-write on an In-progress record only; never a create |
| `BrowseController.restart()` -> `restarted()` | writes seconds 0 and keeps the best, then `show` -> `puzzleShown` **adopts** them; `puzzleShown` never writes and never flushes the outgoing puzzle, so a later flush can only write the new attempt |
| `resetAllProgress()` -> `afterReset()` | the store erases first; `afterReset()` re-reads and zeroes the memory; nothing is written back |

`puzzleShown(id, progress)` runs at the **end** of `SessionHost.show` (after the new session is shown and restored): it first accrues the open interval to the outgoing puzzle's in-memory seconds (already merged by the preceding `persist` in `open()`), then adopts `progress.puzzleSeconds` and `progress.bestSeconds`. If the restore failed and a fresh New session is shown (`SessionHost`'s fallback), `show` passes `NEW.copy(bestSeconds = progress.bestSeconds)`.

**5.2 The solve signal (`byAid`).** `PlaySession` gets `var solvedListener: (byAid: Boolean) -> Unit = {}`, called at the same two sites as the constructor's `onSolved` (immediately after it, before `settled()`); `SessionHost.build` sets it right after `newSession` returns, as it does `onEvent` (WO-007 DA-123). **`SessionHost`'s internal constructor does not change**, so `HeldSolveNowStoreTest` (`REQ-046.A3`) and `SessionHostScaffoldingTest` keep compiling untouched (their SHA-256 is compared before and after the tasks that touch `play` and `app`). `SessionHost` gains `var time: PlayTimeKeeper? = null`, set by `AppViewModel`; unset (tests of the bare host) it changes nothing. Inferring "by the aid" from "SOLVE without a LOCK" in `PlayEvent` was rejected: it would couple time to a sequencing detail of a sound enum.

**5.3 The inputs.**
- **Touch:** in `TangramContent`, `Modifier.pointerInput(time) { awaitPointerEventScope { while (true) { val e = awaitPointerEvent(PointerEventPass.Initial); if (e.changes.any { it.pressed || it.previousPressed }) time.touch(pressed = e.changes.any { it.pressed }) } } }` on the **root `Box`**, so the board, the top bar, the solved bar, the grid and the settings overlay are all covered, it never consumes, and Compose UI tests (which inject into the Compose view, bypassing `Activity.dispatchTouchEvent`) exercise the same path. `touch` accrues first, then records `lastTouchMs = now`; the work per event is a few arithmetic operations, and a state write happens only when a whole second or a flag changes.
- **Running:** `LaunchedEffect(time, host, controller, settings) { snapshotFlow { ActiveSecond.puzzleCounts(host.state, settings.isOpen, controller.gridOpen) }.collect(time::setPuzzleRunning) }`. One declarative derivation, no hook in `settings`, `browse` or `play`. It lags a state change by at most one frame (16 ms), harmless; the solve does not depend on it (`solved` stops the clock itself).
- **Visible:** `MainActivity.onStart` -> `time.setVisible(true)`; `onStop` -> `time.setVisible(false)` (which flushes) **before** `store.sync()`; `onPause` -> after the existing `persist()`, `time.flush()`.
- **Rotation (C9):** the keeper lives in `AppViewModel`, which survives rotation and `recreate()`; the stop/start pair credits nothing for the gap and keeps the touch window, so the value is kept and counting continues.

**5.4 The ticker: nothing runs when idle.** `CountingTicker` (`app`, an `android.os.Handler` on the main looper; no new dependency) posts `time.accrue()` every 1000 ms **only while `keeper.counting` is true**; the keeper reports changes through `onCountingChanged`, and `counting` becomes false by itself when the window expires (the next accrual notices), so the ticker stops within one second of the expiry, on background, and at no other time. While the player is playing the screen is on and the ticker is one 1 Hz message. `onCleared` stops it. A missed tick costs nothing (interval accrual). 1 s keeps the on-board timer exact and bounds the midnight mis-attribution to 1 s.

### 7. The timer on the board (REQ-031) *(item 4)*

## Risks & edge notes

- **Highest risk, for the Design Reviewer's spot-check: who writes `puzzleSeconds` and `bestSeconds`, and in what order** (section 5.1). Four writers touch two fields (the capture merge, the 10 s flush, `restarted()`, the reset) next to `BrowseController`'s own writes of the same record; a wrong order **silently resurrects a stale or erased time** (a flush after Restart; a reset followed by a late flush; a leave that drops the last second; a flush that creates a record whose state is New). The design answers each with an adopt-only `puzzleShown`, a merge keyed to the current puzzle id with `NEW` forced to 0, a flush that never creates, and a reset that re-reads before anything can write. The reviewer's targets: the order inside `open()` (persist, then show), `restart()` (store write, then show), `confirmReset` (store, `afterReset`, `time.afterReset`), and the mid-drag flush. `OwnershipOrderTest` encodes every one of them.
- **A product-semantic risk (owner item 1): today and total count browsing and settings time.** Read literally from TYPE-005 and REQ-029/032 and matching the prototype; the alternative is a one-line gate. If Jami reads "play time" as "solving time" this is the number he will notice first.
- **The 60 s idle cut-off against a child who thinks for a long time.** Locked in TYPE-005 as an ASSUMPTION; a player who studies a puzzle for two minutes without touching it is not counted for the second minute. A held finger is counted (DA-134). Tunable in one constant, but changing it is a CHG, so it is owner item 2 for the playtest.
- **Not counted as touch:** a hardware key press and a TalkBack double-tap (accessibility actions do not arrive as pointer events). #Accessibility is an idea; a keyboard or TalkBack player's time would read low. Accepted, noted for CA-10.
- **Clock drift and testability:** interval accrual from `System.nanoTime` means no drift to correct (the tick period is irrelevant), and the clock is injected, so no test waits. Residual: `SystemTimeSource` itself is covered only by a smoke test.
- **Midnight:** the interval ending after the date change belongs to the new day (at most 1 s mis-attribution with the 1 Hz ticker); a stored date later than today (the clock set back) counts as "differs" (F28); a time-zone change moves "today" with `LocalDate.now()`; a session idle across midnight rolls on the next touch. Documented, tested with a settable `today()`; the real `LocalDate.now()` is untestable on a device without changing its clock (not done, `Settings` access would be a permission-adjacent action).
- **Battery:** no polling when idle: the ticker exists only while `counting`; at most one 1 Hz Handler message while the player plays with the screen on; a write per 10 s. `counting` goes false on the first accrual after the window expires.
- **API 26 lifecycle:** `onStart` / `onStop` is the only visibility signal; on API 26 a locked screen still delivers `onStop`; multi-window is out of scope (F3), and the 60 s window bounds any visibility mistake to one minute per touch. `java.time` is available from API 26 (F9). Rotation on tablets is `onStop` then `onStart` on the same ViewModel.
- **Save cadence:** a settled event writes the board and the time in one write (the existing persist), plus one flush per 10 s while counting; a write mid-drag is a few KB, atomic, on the main thread (the same cost as a settled event; watched at the playtest). `store.sync()` stays in `onStop`.
- **Old saves:** puzzles solved in WO-004 to WO-007 builds have no best (null, shown `–`) and 0 seconds; this is the existing DA-77 meaning, no migration. DA-66's "a complete In-progress save becomes Solved" restores without a solve event, so it sets no best.
- **The timer pill and the outline:** reserved corner, translucent, inert; on a board under about 320 dp high it can touch an outline corner (recorded by the sweep, not asserted).
- **`SettingsController` parameter order:** new parameters sit before `onReset` because the WO-007 tests use trailing-lambda syntax.
- **Release safety:** no new permission, library, manifest element, sound or haptic caller; `TestConfig.timeSource` and the debug `timeSource` are in `debug` only (the release twin passes through, asserted); V-04, V-08 (+ `--expect-debug`) and the feedback-caller check re-run at the close; the keeper has no `tick` or `play` member (scan rule 4).
- **Owner-checkpoint items (Jami):** (1) does browsing and settings time count in "today" and "total" (the design: yes, as TYPE-005 reads), or only solving time; (2) the 60 s idle cut-off against a long think (keep, or ask for a different limit); (3) the timer's look and corner on a real phone and tablet (a pill, 0:00 on a New puzzle, hidden when solved); (4) the settings order and wording (all labels are prototype strings accepted at G1; no new AI Finnish); (5) hours display (`1 h 5 min`) on the solved bar and in the list.
- **The v1 save format.** Unchanged; tests seed stored states through the existing store only.
