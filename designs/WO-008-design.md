**In one paragraph.** Time is counted from **timestamps, not ticks**: a small pure rule in `kernel` (TYPE-005) credits the part of each interval that was visible and within 60 s of a touch, and a new `time` module owns the accumulator (`PlayTimeKeeper`), fed by a **monotonic, injectable `TimeSource`** (tests never wait). Puzzle time counts only while an In-progress puzzle is shown with no settings or grid on top; today and total count every active second (the owner confirmed this reading). **Everything fits the frozen v1 format**: no field, no migration, no contract edit. **(rev 1)** The keeper separates **accounting** (in memory, used by every input, never touches the store) from **writing** (a short, closed list of paths), so no input can write a stale value, and the reset is safe **by construction**, not by call order. The keeper's seconds reach the store through the existing persist path (a merge in `SessionHost.capture` that computes the best from the stored base) plus a guarded 10 s flush. The settings screen gets the timer row first and a play-time section after sound through a one-method readout seam. The on-board timer is an inert pill in the board's top-right corner that **steps aside for the Restart and DEV controls at their measured positions**; it changes no existing layout.

### 1. Module shape (G-06) *(item 6)*

**`time` is confirmed as the code home** (`build-map.md` §1), a new Android library: `include(":time")`, `time/build.gradle.kts` a copy of `settings`' (android-library + compose plugin, `implementation` of `:kernel`, `:contracts`, the BOM and `compose.foundation`; test scope as `settings`, no `:store`, no `:content`). **Main scope: `kernel` + `contracts` only**, exactly V-06's `time: {kernel, contracts}`; only `app` depends on it, so no cycle is possible. No manifest. Namespace `io.github.jamisuni.tangram.time`.

**The split inside:**
- **`kernel` owns the TYPE rules** (architecture §3): `ActiveSecond` (the 60 s rule and "which screens let the puzzle count") and `DurationFormat.parts` (the m:ss / h min split, used by `browse`, `settings` and `time`, each holding the two format strings). Pure, JVM-tested.
- **`time` owns counting** (O-04): `PlayTimeKeeper`, `TimeSource`, `PuzzleTimer`. No Android type in the keeper (a plain Kotlin class with Compose snapshot state, as `PlaySession` does), so its tests are JVM.
- **`settings` and `time` never depend on each other** (G-06). The settings screen reads today and total through a one-interface seam it owns (`PlayTimeReadout`), implemented in `app` over the keeper; the best-time list reads the store and the library it is handed (section 6).

**Why not no new module:** `time` is named by `architecture.md` §3, O-04, O-06, O-08 and `build-map.md` §1, and trace-check rule 3 wants the covering tests under the code home. **Why not everything in `kernel`:** snapshot state and a composable do not belong in a JVM module.

### 2. The time model (TYPE-005, the active second) *(item 1)*

**2.1 What is active: `ActiveSecond.activeMs(prevMs, nowMs, visible, lastTouchMs, touching)`.** Of the interval (`prevMs`, `nowMs`] it returns the milliseconds that were **visible and within 60 s of a touch**:

```
if (!visible || nowMs <= prevMs) 0
else if (touching) nowMs - prevMs                     // a finger is down: engaged
else if (lastTouchMs == null) 0                       // never touched since the process started
else max(0, min(nowMs, lastTouchMs + 60_000) - max(prevMs, lastTouchMs))
```
`IDLE_LIMIT_MS = 60_000` is TYPE-005's locked ASSUMPTION, one constant. The window is inclusive ("at most 60 s ago"), so 5 minutes untouched credits exactly 60 s (REQ-029 A1: "at most 60 s"). This is what the owner asked for ("if havent done anything for minute then stop counting time until next press"): counting stops a minute after the last touch and the next touch resumes it.

- **"Visible":** the Activity is **started** (`onStart` … `onStop`). Not a frame or composition test (an idle board schedules no frames, WO-003).
- **"Touch":** a pointer **contact**: any pointer event in which a pointer is pressed or was pressed (down, move, up, cancel), observed at the app root (5.3). Hover and key presses are not touches. **A finger held down counts as engaged** (`touching`), cleared on the up, on cancel and when the app stops being visible. This is a softening of the prototype and of the owner's wording (a perfectly still contact would otherwise stop counting after a minute; on real touchscreens a held finger usually streams small moves, so it matters mostly on emulators and in tests). It is kept (DA-134) and put to the owner as one yes/no with the key press and the counted minute (owner items).
- **Interval accrual, not tick counting.** Each input first closes the open interval **in memory** under the **old** flags (`account`, 5.1), then changes the flag. A late or dropped tick, a stall and a device sleep neither lose nor invent time (a sleep is bounded by the 60 s window, and `System.nanoTime` does not advance in deep sleep); one 5-minute jump credits what 300 one-second steps credit.
- **Sub-second remainders** are carried in memory and only whole seconds are committed, so nothing is rounded up and a restart loses under 1 s.

**2.2 What pauses what.**

| Situation | Puzzle time | Today and total |
|---|---|---|
| Visible, touched within 60 s, an **In-progress** puzzle shown, no overlay | counts | counts |
| New puzzle shown (a tray tap or turn, REQ-030 A3) | **no** | counts |
| Solved puzzle shown | no | counts |
| All-puzzles grid open (REQ-050) | no (F28: grid pauses) | counts |
| Settings open (`isOpen`, REQ-032) | no | counts while the player touches it |
| Browsing to another puzzle (‹ ›, grid) | the shown puzzle's own seconds, adopted from the store | counts |
| Backgrounded, screen off, rotation gap (about 100 ms) | no | no |
| Untouched for more than 60 s | no | no |
| Finger held down | counts | counts |
| Process death or crash | resumes from the last save (4.3); **not counting until the first touch** | same |

The puzzle clock's gate is `ActiveSecond.puzzleCounts(state, settingsOpen, gridOpen) = state == IN_PROGRESS && !settingsOpen && !gridOpen` (TYPE-006: "time is counted only In progress", scoped by its own "(REQ-030)"). **When a puzzle's time starts (REQ-030 A3):** exactly when TYPE-006 moves New to In progress, a drag starting on a tray piece (`PuzzleStates.onTrayDragStarted`); tapping or turning a tray piece leaves it New. The time **stays** In progress when the piece is sent home (the empty In-progress board).

**2.3 The idle cut-off against a child who thinks for a long time.** TYPE-005 is locked at 60 s; a player who studies a puzzle for two minutes without touching it is not counted for the second minute. The owner's own message asks for the same rule. It is the playtest item for the constant (risks).

**2.4 The clock: an injectable `TimeSource`** (WO-003's precedent, E5):

```
interface TimeSource { fun nowMs(): Long  /* monotonic */ ; fun today(): java.time.LocalDate /* local date */ }
object SystemTimeSource : TimeSource       // System.nanoTime() / 1_000_000 ; LocalDate.now()
```
`System.nanoTime` is monotonic, immune to wall-clock and time-zone changes, JVM-callable and stops in deep sleep. Tests use a `ManualTimeSource` (a fake each kit owns). **Device tests** swap it through a debug-only seam (5.5) so **nothing ever sleeps**: a test advances the manual clock and calls the public `keeper.accrue()` on the main thread (through the kit's `advanceActive`, 8).

### 3. Solve time, best time, attempt time, reset *(item 2)*

- **When the solve time is fixed:** at the **solve event** (the completing drop inside `release()`, before the 2.4 s timeline). `keeper.solved(byAid)` accounts the open interval, freezes `puzzleSeconds`, stops the puzzle clock, and records a **pending own-solve result** (`puzzleSeconds` for a player's solve, none for an aid solve).
- **Where "its solve time is available" (REQ-005 A1) lives:** the `puzzleSeconds` of the **Solved** record, written by the same persist that writes the state (5.1). It stays until Retry (`restarted()` resets it to 0), so after a slower re-solve it holds the new attempt's time while the best keeps the faster one. A reading (DA-136, CA-10): REQ-026 asks for "the best time", so no separate solve-time element is added (D4).
- **Best time, computed from the stored base (rev 1, F1d):** `mergeInto(id, base)` returns `base.copy(puzzleSeconds, bestSeconds)` with `bestSeconds = min(base.bestSeconds ?: MAX, pendingOwnSolve)` when a player's own solve is pending, else `base.bestSeconds` unchanged. **The keeper holds and caches no best**, so it can never write back a stale one (O-08), and it exposes none (no reader needs it: the solved bar and the settings list read the store). Equal keeps; `0` is a legal value and differs from `null` (shown `–`). The pending result is cleared by `puzzleShown` and `afterReset`.
- **An aid solve never sets a best** (REQ-030 rule 4, REQ-046 A3, the WO-005 regression): `solved(true)` freezes the seconds counted so far and records no pending result, so the merge leaves the stored best as it is. It amends DA-77 ("`puzzleSeconds` untouched") to "the seconds counted so far".
- **Retry and Restart:** `BrowseController.restart()` writes `progress.restarted()` (seconds 0, best kept) then shows the puzzle; `puzzleShown` **adopts** the stored 0. The next attempt counts from 0 (REQ-030 rule 2).
- **Reset (REQ-034, DA-120: settings are kept) (rev 1, F1):** the store erases puzzles, bests and play time and keeps `settings` and `lastShown`. `SettingsController.onReset` becomes **`{ time.afterReset(); controller.afterReset() }`**: `afterReset()` is the **first statement**, so no keeper code runs between `store.resetAllProgress()` and it. It discards the open interval (no credit), zeroes today, total, the puzzle seconds, the pending result and the carries, re-reads the (erased) play time from the store, restarts the flush clock at `now`, and **writes nothing**. `controller.afterReset()` then reaches `puzzleShown`, which can only adopt (it has no write path), so the erased values cannot return. Even a flush that falls due afterwards writes post-reset zeros.

### 4. Persistence against the frozen v1 format, and the row-11 analysis *(item 5)*

**Decision: fit everything into the v1 fields. No format change.** Governance row 11 (hard-stop 2, `ai+inform`, mandatory migration test) is **analysed and not triggered**; it is logged and surfaced at the checkpoint.

**4.1 The field map**

| Need | v1 field (`progress.json`) | Notes |
|---|---|---|
| The current attempt's active seconds (REQ-030, the timer) | `puzzles.<id>.puzzleSeconds` (Long >= 0) | 0 when New; frozen at the solve; reset by `restarted()` |

**4.3 When and how often to save, and the loss bounds (ADR-005, O-08) (rev 1: N8)**

The keeper holds live seconds in memory; the store receives them by these routes only (main thread, atomic whole-document writes, an equal save is skipped by the store):

1. **On every settled puzzle event, on leaving a puzzle and on `onPause`:** `SessionHost.capture` merges the keeper's seconds, and the best computed from the stored base, into the captured progress, so they ride the **one** write `BrowseController.persist` already makes. `mergeInto` only returns a value.
2. **`keeper.flush()`** makes **two** whole-document writes when a puzzle is shown: `store.savePlayTime(PlayTime(day, today, total))`, then, for the shown puzzle, a read-modify-write of `puzzleSeconds` **only when the stored record is In progress and the value differs**. It never creates a record, changes `state` or `pieces`, writes a best, or touches the session, so it is safe mid-drag (it does not use `toProgress`). **When (the closed list):** `accrue()` when at least 10 s of source time have passed since the last flush while counting; `accrue()` when counting becomes false (idle expiry); `setVisible(false)`; `setPuzzleRunning(false)`; `onPause`; `onStop` (before `store.sync()`).
3. The solve is saved by route 1 (the completing event's `settled()` runs right after `onSolved`).

| Event | Loss |
|---|---|
| Normal exit, home button, screen off, swipe from recents, a system kill while backgrounded (always after `onStop`) | **0** |
| A puzzle event (lock, return, turn, solve) then a crash | the seconds since that event or the last flush, **at most 10 s** |
| A crash or battery pull while playing | at most 10 s of puzzle, today and total, plus under 1 s of carry; **during the first drag of a New puzzle the stored state is `new` until the drop (DA-49), so a kill mid-drag also loses that drag's puzzle seconds (F4: "a kill loses at most the drag in progress")** |
| A kill between the flush's two writes | the play time is saved and the puzzle seconds are behind by at most 10 s |
| A power cut without `onStop` | as above, plus whatever the OS has not flushed (the existing store behaviour) |

**Disk churn:** at most **two** small writes per 10 s while counting (one flush), none while idle, plus the writes the board events already make (those carry the time, no extra write). **Battery:** no polling when idle (5.4).

**4.4 One reading against O-08 (logged, DA-137).** O-08 says "no slice keeps a stored record across events". The keeper keeps **counters** (today, total, the puzzle's seconds), not a record: it is the sole writer of the play time, writes whole values from counters it owns, and `afterReset()` is O-08's "reload after reset" clause. **It keeps no copy of any stored record's other fields, and (rev 1) none of the best**: every write of `state`, `pieces`, `bestSeconds` and `settings` is a read-modify-write from the store.

### 5. Wiring and ownership of the seconds *(items 1, 2, 6)*

**5.1 Account, then write: one owner, a closed list of writers (the highest-risk part, rev 1).** While a puzzle is shown the keeper's memory is authoritative for exactly one stored field, `puzzleSeconds`; `BrowseController` is authoritative for `state` and `pieces`; the best is always derived from the stored base.

**`account()` (private) closes the open interval in memory** (credits whole seconds and carries, sets or rolls `day` **only when it credits at least one whole active second** (a zero credit leaves `day` as it is, so `NONE` stays `NONE`; rev 2), moves `lastMs` to now, reports a change of `counting` through the callback). It has **no path to the store**. Every input calls it and nothing else: `touch`, `setVisible`, `setPuzzleRunning`, `puzzleShown`, `solved`, `mergeInto`. **`accrue()` (public) = `account()` + the due-flush check**, and it is called by the ticker and by tests only. The paths that write are the closed list in 4.3 (2). Consequence, stated and tested: `puzzleShown`, `touch`, `solved`, `mergeInto` and `afterReset` **cannot write**, so no ordering of them against `open()`, `restart()` or the reset can write a stale value.

| Writer of a stored time field | Order guarantee |
|---|---|
| `SessionHost.capture` -> `mergeInto(id, captured)` | applies **only when `id` is the keeper's current puzzle**; accounts first (a leave loses no second); a `NEW` captured state forces 0; best from `base`; the result is written by `persist`'s one `saveProgress` |
| `keeper.flush()` | the closed list in 4.3; In-progress records only; never a create |
| `BrowseController.restart()` -> `restarted()` | writes seconds 0 and keeps the best, then `show` -> `puzzleShown` **adopts** the 0 (no write, no flush of the outgoing puzzle), so a later flush can only write the new attempt |
| `resetAllProgress()` -> `time.afterReset()` | the store erases first; `afterReset()` is the first statement of `onReset`, discards, re-reads, zeroes and writes nothing; `puzzleShown` after it only adopts |

`puzzleShown(id, progress)` runs at the **end** of `SessionHost.show`: it accounts the open interval, adopts `progress.puzzleSeconds`, clears the pending own-solve result and records `id`. If the restore failed and a fresh New session is shown, `show` passes `NEW`.

**5.2 The solve signal (`byAid`).** `PlaySession` gets `var solvedListener: (byAid: Boolean) -> Unit = {}`, called at the same two sites as the constructor's `onSolved` (immediately after it, before `settled()`); `SessionHost.build` sets it right after `newSession` returns, as it does `onEvent`. **`SessionHost`'s internal constructor does not change**, so `HeldSolveNowStoreTest` (`REQ-046.A3`) and `SessionHostScaffoldingTest` keep compiling untouched (SHA-256 compared before and after the tasks that touch `play` and `app`). `SessionHost` gains `var time: PlayTimeKeeper? = null`, set by `AppViewModel`; unset it changes nothing.

**5.3 The inputs.**
- **Touch:** in `TangramContent`, `Modifier.pointerInput(time) { awaitPointerEventScope { while (true) { val e = awaitPointerEvent(PointerEventPass.Initial); if (e.changes.any { it.pressed || it.previousPressed }) time.touch(pressed = e.changes.any { it.pressed }) } } }` on the **root `Box`**, so the board, top bar, solved bar, grid and settings overlay are covered, it never consumes, and Compose UI tests (which inject into the Compose view, bypassing `Activity.dispatchTouchEvent`) exercise the same path.
- **Running:** `LaunchedEffect(time, host, controller, settings) { snapshotFlow { ActiveSecond.puzzleCounts(host.state, settings.isOpen, controller.gridOpen) }.collect(time::setPuzzleRunning) }`. It lags a state change by at most one frame; the solve does not depend on it. **(rev 1, N2)** A device test that changes the screen and then jumps the clock must let the gate emit first, or the jump is credited under the old flag: the kit's `advanceActive(ms)` does `waitForIdle`, advances the source, calls `accrue()` on the main thread, then `waitForIdle`. A test with a paused Compose clock (`startClockPaused()`) never emits and must not assert time.
- **Visible:** `MainActivity.onStart` -> `time.setVisible(true)`; `onStop` -> `time.setVisible(false)` (a stop point) **before** `store.sync()`; `onPause` -> after the existing `persist()`, `time.flush()`.
- **Rotation (C9):** the keeper lives in `AppViewModel`, which survives rotation and `recreate()`; the stop/start pair credits nothing for the gap and keeps the touch window.

**5.4 The ticker: nothing runs when idle (rev 1, N4).** `CountingTicker(post: (Runnable, Long) -> Unit, cancel: (Runnable) -> Unit, onSecond: () -> Unit)` in `app`; production builds it over a main-looper `android.os.Handler` (`CountingTicker.main(onSecond)`; no new dependency), so a JVM test passes two fakes and needs no `Handler` (the `app` unit tests run against stubbed android.jar). It re-posts `onSecond` every 1000 ms **only while `keeper.counting` is true**; the keeper reports changes through `onCountingChanged`, and `counting` becomes false by itself when the window expires (the next `accrue()` notices), so the ticker stops within one second of the expiry, on background, and at no other time. `onCleared` cancels it. A missed tick costs nothing (interval accrual); 1 s keeps the on-board timer exact and bounds the midnight mis-attribution to 1 s.

- **Naming constraint (rev 1, N5):** no function, local function, lambda-bound name, property or reference named **`tick`** or **`play`** in **any new file in `time/src/main` or `app/src/main`** (`CountingTicker`'s callback is `onSecond`, the keeper's entry is `accrue`). `FeedbackPathScanTest` rule 4 fails on all four forms in every scanned file: `.tick(` / `.play(`, `::tick` / `::play`, bare `tick(` / `play(` (CR-6 N2) and declarations; its trees are every `*/src/main/**`.

### 7. The timer on the board (REQ-031) *(item 4)*

- **What and when:** `PuzzleTimer(shown, seconds)` in `time` renders a small pill with the puzzle time, tag `puzzle-timer`, tabular digits, ink on a translucent paper background, drawn with `BasicText` and a rounded `Box` (no canvas path, DA-92). `shown` is `settings.timerShown` (default false: **A1**). It shows the **current puzzle's** seconds, `0:00` on a New puzzle (the prototype does; F28's open point, DA-140), and is **not composed on a solved puzzle** (the solved bar carries the best; the prototype hides it too).
- **It takes no touch:** a plain text node (no click action, no pointer input). REQ-037's 48 dp concerns the **setting switch** (C6); the walk asserts the pill inert.
- **Where, and how it avoids the controls (rev 1, S3; rev 2, E3).** `PlayArea` gets a slot `timer: (@Composable BoxScope.() -> Unit)? = null`, composed over the board **only while not solved**. It is placed by a new pure `PlayLayout.timerRect(layout, obstacles: List<RectDp>, widthDp, heightDp): RectDp`: the board rect's **top-right**, inset 8 dp, width capped at the area width minus 16 dp; **if that rect comes within 4 dp of an obstacle it steps below that obstacle** (top = obstacle bottom + 4, right-aligned), repeating for the next obstacle. The obstacles are the **real rects** of the Restart control (`placed.second`, whatever corner or strip `computeWithCorner` chose) and the DEV pill (`placeSecondary`'s result). If no legal rect exists above the tray it returns the plain top-right rect (recorded). `PlayArea` measures the secondary control and the timer in **one** `SubcomposeLayout`, places the secondary by `placeSecondary`, then the timer by `timerRect`, and **the timer's size never feeds the layout** (DA-74 parity).
- **The pill does not move within an attempt (rev 2, E3).** Two rules: (a) **the Restart rect is an obstacle even while Restart is hidden** on a New puzzle (`unplacedUnless` keeps its measured size and placement), so the pill is already where it will be at the first drag; (b) the **step decision is made from a template width, not the live text**: `timerRect` is given the width of the widest text the pill can show in the current language and font scale (`88 h 59 min`, measured once in the shared `SubcomposeLayout`), and the pill is drawn right-aligned at its live width inside that placement. So in Finnish at font scale 2.0 on 360 dp the pill cannot jump down by one control height at 10:00 or at 1 h. The cost: where the template overlaps a wide Restart the pill always sits below it, even with a short text.
- **Release has no DEV pill (rev 2, E4).** The release `DebugAids` twin composes nothing in the secondary slot, so where debug steps the pill below a top-right DEV pill, release keeps it in the corner; **the pill's place, never the board, may differ between debug and release**, and the device tests (debug) cannot see the release case. The sweep therefore runs both configurations, with and without a secondary obstacle (DA-140).
- **Why this instead of reserving the corner (S3, answered).** The rev 0 `reserveTopRight` flag changed where Restart and DEV go for every puzzle and window (a Restart pushed to a strip shrinks the board; DEV could lose its last corner), turned the existing sweeps into tests of a configuration the app does not run, and still could not hold the pill and a wide Finnish Restart on a 360 dp phone at font scale 2.0 (about 250 dp + about 100 to 150 dp in a 352 dp row). An obstacle placed from the real rects changes **no** existing placement, **DA-71 and DA-75 stand untouched** (their sweeps still describe the app), cannot make DEV unplaceable, never shrinks a board, and keeps the pill at the board's top-right whenever that corner is free. The cost: the pill's vertical position varies, from the corner down by one control height when Restart or DEV sits there.
- **Tests, with real widths (S3).** (a) `TimerPlacementSweepTest` (JVM, `play`): every packaged puzzle x the five reference windows x Restart widths (fi and en at font scale 1.0 and 2.0) x pill widths (`59:59`, `10 h 59 min`, at scale 1.0 and 2.0) x the real `placeSecondary` result **and the no-secondary (release) configuration** x the template width; asserts the pill's rect is the same for every live text of an attempt; asserts the pill never overlaps either obstacle, stays inside the area and above the tray, and that the no-legal-rect fallback count is **0**; **records** (not asserts) how many puzzles' pills touch the outline. A nonzero fallback count is a design finding back to the Design Author, never a loosened test. (b) **A device-measured test** `TimerLayoutMeasuredAppTest` (visible, `app/src/androidTest`, TASK-T8a): on `PHONE_360x780` in **Finnish at font scale 2.0** with an In-progress puzzle seeded to **10 h 59 min** and the timer on, it reads the real bounds of `puzzle-timer`, `restart-button` and (debug) the DEV pill and asserts no intersection, the pill inside the play area and the board rect's top-right edge respected when free; the same on `PHONE_390x844` English 1.0 and `TABLET_1280x800`. It **records the measured widths** in the workorder. The JVM sweep's width bounds start as design bounds (Restart at most 280 dp, pill at most 170 x 44 dp) and are **raised by the Test Author if the measured widths exceed them**, at a named step (MEASURE-8, section "Suggested cut") before MOVE-JVM8.
- **Honest limit:** the silhouette fits at most 82 % x 80 % of the board rect, so the corner is clear of the outline when the board is at least about 320 dp high; on a shorter board the translucent pill can touch an outline corner (recorded by the sweep).

**Value shapes, stated exactly.**
- `activeMs`: `touching` with `visible` credits the whole interval; `lastTouchMs == null` credits 0; a touch exactly 60 000 ms before `nowMs` credits through `nowMs` and not a millisecond more; an interval wholly beyond the window credits 0; `visible == false` credits 0.
- `PlayTimeKeeper`: after `touch`, 300 s of source time and `accrue()`, today and total rose by **exactly 60**; the same in 300 one-second steps; with the puzzle clock off for 120 s of touched time `puzzleSeconds` is unchanged and today and total rose; `solved(false)` then `mergeInto` gives `puzzleSeconds == solve time` and `bestSeconds == min(base best, solve)`; `solved(true)` leaves `bestSeconds == base.bestSeconds` **even when the counted seconds are below it**; a best changed in the store between adoption and the merge is respected (nothing cached); `mergeInto` for another id returns its input; `flush()` never writes a record whose stored state is not In progress; **`puzzleShown`, `touch`, `solved`, `mergeInto` and `afterReset` make no store call at all**, whatever is due; `afterReset()` leaves `todaySeconds == totalSeconds == 0` and the next flush writes only post-reset seconds.
- Midnight: the interval that ends after the date changed belongs entirely to the new day; a stored `day` that differs from `source.today()`, earlier **or later**, restarts today at 0 (F28); total is never reduced.
- **(rev 2, E2)** After `afterReset()`, any number of `account()` calls with zero credit leave `PlayTime` as `NONE` (`day == null`), and `flush()` then writes nothing (the store skips an equal save). A `day` is set or rolled only by an account that credits at least one whole active second.
- `DurationFormat.parts(3599)` is `59:59`, `parts(3600)` is `1 h 0 min`, `parts(0)` is `0:00`.
- `timerRect` with no obstacle in the way is the top-right rect inset 8 dp; with an obstacle within 4 dp it sits 4 dp below the obstacle, right-aligned.

## Risks & edge notes

- **Highest risk, for the Design Reviewer's spot-check: the writers of the stored time fields and their order** (5.1). Rev 0 failed here (the reset). Rev 1 removes the class of bug rather than one order: inputs only account, the writers are a closed list, `afterReset()` is the first statement of `onReset` and writes nothing, the best is never cached. Targets: the two lists in 4.3 and 5.1 against the code, the nine `OwnershipOrderTest` cases (a flush due at reset, `open()`, `restart()`, an aid solve, a long first drag), and the order inside `open()` (persist, then show), `restart()` (store write, then show), `confirmReset` (store, `afterReset`, `controller.afterReset`).
- **A product-semantic point, now closed: today and total count browsing and settings time.** Literal REQ-029 / TYPE-005 and the owner's answer ("can be total time"); no CHG needed.
- **The 60 s idle cut-off against a child who thinks for a long time.** Locked in TYPE-005 and asked for in the owner's own words; a held finger is counted (DA-134). Tunable in one constant, but changing it is a CHG.
- **Not counted as touch:** a hardware key press (the prototype counts `keydown`; TYPE-005 says touch) and a TalkBack double-tap. #Accessibility is an idea. Listed for the owner.
- **Live counting versus existing tests:** `HeldResetAppTest` is a named casualty with a corrected check (S1); `HeldSolvedFindAppTest` stays green only by sub-second margin: a red there routes through N2 (the clock moved before the gate emitted) before the product.
- **Clock drift and testability:** interval accrual from `System.nanoTime` has no drift to correct; the clock is injected, so no test waits. `SystemTimeSource` itself is covered by a smoke test only.
- **Midnight:** the interval ending after the date change belongs to the new day (at most 1 s with the ticker); a stored date later than today counts as "differs" (F28); a time-zone change moves "today" with `LocalDate.now()`; a session idle across midnight rolls on the next touch. The real `LocalDate.now()` is not tested by changing the device clock.
- **Battery:** the ticker exists only while `counting`; at most one 1 Hz message while the player plays with the screen on; at most two small writes per 10 s.
- **API 26 lifecycle:** `onStart` / `onStop` is the only visibility signal; on API 26 a locked screen still delivers `onStop`; the 60 s window bounds any visibility mistake to one minute per touch. `java.time` is available from API 26 (F9). Rotation on tablets is `onStop` then `onStart` on the same ViewModel.
- **Save cadence:** a settled event writes the board and the time in one write; one two-write flush per 10 s while counting; a flush mid-drag is a few KB, atomic, on the main thread (watched at the playtest). `store.sync()` stays in `onStop`. A kill mid-first-drag loses that drag's seconds (4.3).
- **Old saves:** puzzles solved in WO-004 to WO-007 builds have no best (null, shown `–`) and 0 seconds (the existing DA-77 meaning, no migration). DA-66's complete-In-progress restore sets no best.
- **The timer pill's position varies** by one control height when Restart or DEV sits at the top-right; on a board under about 320 dp high it can touch an outline corner (recorded by the sweep).
- **`SettingsController` parameter order:** new parameters sit before `onReset` because the WO-007 tests use trailing-lambda syntax.
- **Release safety:** no new permission, library, manifest element, sound or haptic caller; `TestConfig.timeSource` and the debug `timeSource` are in `debug` only (the release twin passes through, asserted); V-04, V-08 (+ `--expect-debug`) and the feedback-caller check re-run at the close; no `tick` or `play` name in any new `src/main` file (5.5).
- **Owner-checkpoint items (checkpoint 8, for the owner):** (1) **one yes/no on the counting edge cases** (rev 1): should a finger resting still on the screen stop counting after a minute (the build counts it), should a hardware key press count as activity (the build does not), and should the minute after the last touch be counted (the build counts it, "at most 60 s ago" is inclusive); (2) the timer's look and corner on a real phone and tablet (a pill, `0:00` on a New puzzle, hidden when solved, no clock glyph, stepping below Restart or DEV when they are at the top-right); (3) the settings order and wording (all labels are prototype strings accepted at G1; no new AI Finnish); (4) the hours display (`1 h 5 min`) on the solved bar and in the list. **Item "does browsing count in today and total" is closed** by the owner's answer of 2026-10-05.
- **The v1 save format.** Unchanged; tests seed stored states through the existing store only.
