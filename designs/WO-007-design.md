## Chosen design

### 0. Shape in one picture

```
play: PlaySession --onEvent (settable property)--> SessionHost.onEvent --(app maps PlayEvent -> FeedbackEvent)--> settings.Feedback.on(e)
                                                          gate: soundOn() ? SoundOut.play(e) [+ HapticOut.tick() on LOCK] : nothing
platform defaults:  TangramApp root { PlatformFeedbackLever.Provide { ... } }   LocalSoundEffect = silent, LocalHapticFeedback = silent,
                    keyboard-focus sounds off by the ui flag  ->  Compose click sound / long-press haptic never reach the platform
settings: SettingsController(store: IProgressStore, canOpen, onReset) ; SettingsGear (⚙, 48 dp) ; SettingsOverlay ; Feedback ; SoundSynth ; AudioTrackSoundOut ; ViewHapticOut
browse:   BrowseTopBar(..., trailing = { SettingsGear }) ; BrowseController.afterReset()
app:      AppViewModel { store, host, controller, settings, feedback, aids }  TangramApp: Box { Column(base) ; AllPuzzlesOverlay ; SettingsOverlay } + BackHandler
persist:  store.settings().copy(soundOn = ...)  -> progress.json "settings.soundOn"   (v1, unchanged)
reset:    confirm -> store.resetAllProgress() -> onReset() = controller.afterReset() -> same puzzle, New, settings kept
```

### 1. Module shape (G-06) *(item 1)*

**`settings` becomes a new Android library** (`include(":settings")`, `settings/build.gradle.kts` a copy of `browse`'s: android-library + compose plugin, `implementation` of `:kernel`, `:contracts`, the Compose BOM and `compose.foundation`; test scope as `browse`, no `:content`, **no `:store`**). **Main-scope dependencies: `kernel` and `contracts` only**, exactly V-06's `settings: {kernel, contracts}`; nothing depends on `settings` except `app`, so no cycle is possible. No `AndroidManifest.xml` in `settings` (as `play`), so V-01 and V-08 see no new element. Namespace `io.github.jamisuni.tangram.settings`.

**From `store`:** `IProgressStore` (an interface in `contracts`), received by constructor injection from `app`; three members: `settings()`, `saveSettings()`, `resetAllProgress()`. It does not see `JsonProgressStore` and does not need `IPuzzleLibrary` now. It does not know `play`, `browse`, the session or the board; "reload what reset erased" is a callback (`onReset`) that `app` points at `BrowseController.afterReset()` (O-08); WO-008 adds `time`'s reload to the same callback.

**Why not no new module:** `architecture.md` §3 and build-map §1 already assign `settings` its screen and the sound/haptic output; `app` is the composition root, not a home for slice code (O-09).

### 2. Opening and closing, the ⚙, back, rotation (REQ-032) *(item 2)*

- **An in-app overlay, not a screen, a Dialog or an Activity** (DA-118). `TangramApp` composes `SettingsOverlay` in the root `Box`, on top of the base `Column`, as `AllPuzzlesOverlay` is: `if (settings.isOpen)`, `fillMaxSize`, paper background, `safeDrawing` padding, a `pointerInput { detectTapGestures { } }` that swallows touches. REQ-032 says "over the current puzzle". The base `Column` stays composed underneath, so **the `PlaySession`, its pieces and the clock are never touched: "changes nothing on the board" (A1) holds by construction** (reset excluded, F25) and is then proven by test.
- **Modal for the semantics tree and for input (rev 1, N4).** While the overlay is open:
  - the base `Column` gets `Modifier.clearAndSetSemantics { }`, so the board, tray and top bar are neither reachable by TalkBack nor visible to the walks;
  - **a press that has not yet become a drag:** a finger already down on a piece is not `isDragging`, and its pointer stream stays with `PlayArea` when a second finger taps ⚙. `PlayArea` gets one parameter, `inputEnabled: Boolean = true` (delivered by P-1); `app` passes `!settings.isOpen`. When it turns false, `PlayArea` cancels the gesture machine and calls `session.interruptDrag()` (the path it already runs when it leaves the composition, so the piece returns silently, F5) and ignores new downs. No drag, lock or return can happen under the sheet;
  - **a hardware keyboard (rev 2, E4):** `clearAndSetSemantics` does not stop focus, and `canFocus = false` would not help (it applies to the one node it decorates, and `focusGroup()` is itself a non-focusable target, so ‹ and › nested in the top-bar `Row` would stay focusable). The base gets `Modifier.focusProperties { onEnter = { cancelFocusChange() } }.focusGroup()` while open (the API is in ui 1.12.1), so focus cannot move **into** the base; and **when the overlay opens, focus is cleared** (`LocalFocusManager.clearFocus()`), because a base control may already hold it. `SettingsOverlayScaffoldingTest` **focuses ‹ first, then opens the overlay, then sends Tab and Enter**, and asserts the puzzle did not change. The test is never loosened.
- **No Dialog, Popup or `ModalBottomSheet`:** each creates a second compose root and the REQ-008 A2 walk fails on "a dialog or popup root". The reset confirmation is in-screen too (section 5).
- **State** lives in `SettingsController`, a field of `AppViewModel`: `isOpen`, `confirmingReset`, `soundOn` (snapshot state). It survives rotation and `recreate()` (C10). `rememberScrollState` survives through `rememberSaveable`.
- **Opening** is `SettingsGear` (48 × 48 dp touch area, tag `settings-button`) in the new **`trailing` slot of `BrowseTopBar`** (O-09; default `{}`; placed after `›`, as Spec/02 §2). `SettingsController.open()` does nothing when `canOpen()` is false; `app` passes `canOpen = { !host.isDragging }` (F5). The glyph is drawn in a `Canvas` with `drawLine` and `drawCircle` **in px, no `scale`, no path** (DA-92).
- **The 48 dp (C5):** REQ-037 says 48 dp for every player control; `Spec/02` §4 says 44 for the ⚙. **DA-53 (WO-004) already ruled "WO-007's ⚙ needs 48 dp too"**; nothing new is decided here. The `design-inputs.md` §2 line is added at the close. At 360 dp the top bar holds 52 + title + counter + 52 + 48 dp; the title ellipsizes as it does today (risk list).
- **Closing:** the "Done" button in a header row at the top of the sheet (never below the scroll) and the Android Back button (`BackHandler(enabled = settings.isOpen)`, registered after the grid's so it wins). Closing clears a pending reset confirmation (Back during a confirmation is a cancel, REQ-034 A2). Closing writes nothing and calls nothing.
- **Rotation with it open (C10):** the ViewModel keeps `isOpen` and `confirmingReset`, the overlay recomposes at the new size (tablets rotate, phones are portrait-locked, F3). The sheet is `widthIn(max = 560.dp)`, centred. The test rotates on `[TABLET_1280x800]` and `recreate()`s on `[PHONE_390x844]`.
- **No difficulty control (A2):** the screen holds exactly these interactive nodes (tags): `settings-close`, `settings-sound`, `settings-reset`, and while confirming `settings-reset-confirm` and `settings-reset-cancel`. The tests assert **no other interactive node exists**, and no string of the module matches a difficulty word. The match is **word-marked like `PromiseWords`** (rev 1, N6): WHOLE `easy`, `medium`, `hard`, `level`, `levels`; PREFIX `difficult`, `helppo`, `vaikea`, `keskitaso`, `taso`; an `ALLOWED_WORDS` map (empty) takes a legitimate hit by exact word with its reason, never by loosening a stem. G-07 stays a review check plus this test.
- **Contents and order (REQ-032 rule):** [timer, WO-008] · sound · [play time and best times, WO-008] · reset · how to play · free note · privacy. WO-008 inserts its rows without reordering (DA-124).

### 3. Sound and haptics (REQ-033, REQ-020, REQ-023, REQ-010) *(item 3)*

**3.1 Which events, and the plumbing (DA-115, DA-123).**
- `play` gets `enum class PlayEvent { PICK_UP, TURN, LOCK, RETURN, SOLVE }` and **a settable property** `PlaySession.onEvent: (PlayEvent) -> Unit = {}` (rev 1, F4: no constructor or `SessionHost` seam changes; set by `SessionHost.build` right after `newSession` returns; nothing fires during construction). `settings` has its own `enum class FeedbackEvent` with the same five values; `app` maps one to the other with an exhaustive `when` (no `else`). `play` and `settings` stay independent (G-06).
- **`SessionHost`'s internal constructor `(newSession: (Puzzle, () -> Unit) -> PlaySession, restoreInto)` does not change.** Its consumers are `SessionHostScaffoldingTest` and **`app/src/test/.../held/HeldSolveNowStoreTest.kt:43` (`REQ-046.A3`, an acceptance test): both keep compiling untouched**; no implementer edits an acceptance test. `SessionHost` gains `var onEvent: (PlayEvent) -> Unit = {}` (the `onChanged` pattern) and `build` does `session.onEvent = { onEvent(it) }`.
- Emission points in `PlaySession`, **each placed before `settled()` (rev 1, N3)**: `settled()` runs `onChanged` → `persist` → an atomic file write on the main thread, so the sound must not wait behind disk I/O:
  - **PICK_UP** when `beginDrag` actually starts a drag;
  - **TURN** on a tray tap, a **successful** board tap-turn, a twist step that changes the drag's turn (`setDragTurn` runs on every twist move, so only when the turn differs), and a mirror (tray or board, successful), which uses the turn cue (DA-115);
  - **LOCK** for `DropOutcome.Locked`; **RETURN** for `DropOutcome.Home` (a missed drop or a drop on the tray, REQ-020);
  - **SOLVE** after the LOCK that completes the puzzle, and alone for `solveByAid`.
  - **Silent, by rule:** a refused board turn or mirror (it only shakes: "no sound signals failure"), `interruptDrag`, `restore`, `toProgress`.

**3.2 One gate, and a scan on call paths (rev 1, F2; DA-116, DA-123).** `Feedback(soundOn: () -> Boolean, sound: SoundOut, haptic: HapticOut)` with one method, `on(event)`:

```
if (!soundOn()) return            // the only place the switch is read for output
sound.play(event)
if (event == LOCK) haptic.tick()  // "a lock also gives a short haptic tick ... the tick follows the sound switch"
```
Each out call is in `runCatching` (G-10). `soundOn` is `{ settings.soundOn }`, the controller's snapshot state, which mirrors the store (one writer, section 4).

**The scan makes the gate the only path in our code.** `FeedbackPathScanTest` (JVM, **module `app`**, `app/src/test/.../feedback/`, `// decision DA-116`: it pins the gate, not G-01). Trees scanned: `*/src/main/**`, `*/src/release/**`, `*/src/debug/**` (never `build/`, `.gradle/`, `.swdev/`, `Study/`, `Requirements/`; test trees are not scanned). Inputs: declared in `app/build.gradle.kts` by the DA-88 pattern with **globs** (`scannedFileGlobs` gains `"*/src/debug/**"`; no module names; no word "devtools", DA-89), `repo.root` already passed. Matching is on **identifier tokens** (`(?<![A-Za-z0-9_])name(?![A-Za-z0-9_])`), comments skipped. Four rules:
1. **Forbidden everywhere:** `Vibrator`, `VibratorManager`, `VibrationEffect`, `VIBRATE`, `MediaPlayer`, `ToneGenerator`, `Ringtone`, `RingtoneManager`, `MediaActionSound`, `playSoundEffect`, `SoundEffectConstants`. (Consistent with `PromiseSourceScanTest`, which gains the same `Vibrator`, `VibratorManager`, `VIBRATE`; the two scans no longer disagree.)
2. **Allowed only in `settings/src/main/**/AudioTrackSoundOut.kt` and `ViewHapticOut.kt`:** `AudioTrack`, `AudioAttributes`, `AudioFormat`, `performHapticFeedback`, `HapticFeedbackConstants`. (`SoundPool` is gone with the fallback, N8.)
3. **Allowed only in `app/src/main/**/PlatformFeedbackLever.kt`:** `LocalSoundEffect`, `LocalHapticFeedback`, `SoundEffect`, `HapticFeedback` (as whole identifiers), `isInteractionSoundEffectsEnabled`, `isInteractionSoundEffectOnClickEnabled`, `hapticFeedbackEnabled`, `isSoundEffectsEnabled`, `isHapticFeedbackEnabled`.
4. **Call rule (rev 2, E5: function references too):** the calls `.play(` and `.tick(` **and the references `::play` and `::tick`** (so `haptics::tick` passed as a callback cannot route around the gate) appear only in `settings/.../Feedback.kt`, `app/src/debug/.../FeedbackProbe.kt` (it delegates to the real out) and the two out files (`AudioTrack.play()` lives there). So `model.haptics.tick()` or `sound.play(e)` from `app`, `play` or `browse` turns the scan red.
The scan **fails blind**: it asserts its canaries (`Feedback.kt` contains `.play(` and `.tick(`; the lever file contains `LocalSoundEffect`), else `error()`.

**3.3 Producing the sound without an asset, a licence or the network (DA-114).** **Synthesis in code, played by `AudioTrack`.**
- `internal object SoundSynth` (pure Kotlin, JVM-testable): `fun pcm(event: FeedbackEvent, sampleRate: Int): ShortArray` (mono, 16-bit), `fun durationMs(event: FeedbackEvent): Int`. Starting values, ported from the prototype's `sfx` table (DI-1), softened; **the owner's ear is the only judge, so these are tunable constants, not requirements**:

| Cue | Sound | Length | Peak |
|---|---|---|---|
| PICK_UP | sine 520 → 700 Hz glide | 70 ms | 0.18 |
| TURN | sine 760 Hz | 40 ms | 0.12 |
| LOCK | triangle 1320 Hz + sine 1760 Hz starting 30 ms later | about 90 ms | 0.22 |
| RETURN | sine 300 → 180 Hz glide, **the soft low tone** (REQ-033 rule, REQ-020 rule); the length of the return animation | 180 ms | 0.16 |
| SOLVE | **the REQ-023 4-note chime**: a 100 ms lead-in of silence, then triangle 523, 659, 784, 1047 Hz, one every 110 ms, each 240 ms | about 670 ms | 0.25 |

  Every cue has a 3 ms attack and an exponential decay to zero (the last sample is 0). **The 0.35 cap is per cue** (rev 1, N2): no cue exceeds 0.35 of full scale. A completing drop plays LOCK, then SOLVE; **SOLVE's 100 ms lead-in lets the LOCK click end first, so the two never overlap and the mix never exceeds one cue's peak** (rev 0's LOCK + SOLVE overlap summed to about 0.47). **Each effect is at most 1 s** (REQ-033 rule; F26 reads REQ-023's chime the same way), pinned with a margin.
- **`AudioTrackSoundOut : SoundOut` contract (rev 1, F5, all pinned in the seam row):**
  1. **Sample rate:** the cues are synthesized at the device's native output rate, `AudioTrack.getNativeOutputSampleRate(AudioManager.STREAM_MUSIC)` (fallback 48 000), and `PERFORMANCE_MODE_LOW_LATENCY` (API 26) is requested as a **hint only**; nothing assumes it is honoured. (Rev 0 combined 44.1 kHz with the flag, which a 48 kHz output normally refuses.)
  2. **Build:** `prepare()` is idempotent and starts **one** background thread that builds five `MODE_STATIC` tracks (`AudioTrack.Builder`, API 23; `USAGE_GAME` + `CONTENT_TYPE_SONIFICATION`; mono PCM 16; buffer = the cue's bytes; `write` once, a negative return code counts a build failure).
  3. **Publication:** the five tracks are published as **one immutable `Map<FeedbackEvent, AudioTrack>` through one `@Volatile` field**, assigned once, so the main thread sees all or none.
  4. **Release before prepare finishes:** `release()` sets a `@Volatile released` flag, swaps the published map for an empty one and releases its tracks. `prepare()` checks `released` before building each track, after the last build and **again after publishing**; on a set flag it releases everything it built and publishes nothing. `AudioTrack.release()` is idempotent, so a double release is harmless. Result: no track outlives a released instance, however many `AppViewModel`s a test process creates.
  5. **Replay:** `play(event)` is `val t = tracks[event] ?: return`; skip if `t.state != STATE_INITIALIZED`; `t.stop()`; **`t.reloadStaticData()` must return `SUCCESS`, else `replayFailures++` (an `internal` counter) and return**; `t.play()`; the whole call in `runCatching`. A failed replay is never silent: the counter is asserted by the smoke test.
  6. It takes **no audio focus** and needs **no permission** (`MODIFY_AUDIO_SETTINGS` is not needed for a track). `release()` is called from `ViewModel.onCleared()`.
  7. `internal` for the smoke test: `val ready: Boolean`, `val buildFailures: Int`, `val replayFailures: Int`, `fun trackStates(): Map<FeedbackEvent, Int>`.
- **API 26 vs API 37:** `AudioTrack.Builder` (23), `setPerformanceMode` (26), `getNativeOutputSampleRate` (long-standing) need no version branch. On API 37 a foreground app plays sonification audio without any new permission or focus rule. An emulator with no audio output is a **test finding, not a silent pass** (section 3.6 item 4).

**3.4 Haptics without a permission (DA-114).** `ViewHapticOut : HapticOut` holds a `WeakReference<View>` that `MainActivity` sets in `onCreate` (`window.decorView`) and clears in `onDestroy` (the ViewModel outlives the Activity). `tick()` is `view.performHapticFeedback(HapticFeedbackConstants.CLOCK_TICK)` (API 21, so the same on 26 and 37). **`View.performHapticFeedback` needs no `VIBRATE` permission; `Vibrator` and `VibratorManager` do and are denied by the scan.** It follows the user's system touch-feedback setting, which is what REQ-033 means by "where the device supports it without a permission". The lever of 3.7 does not touch the decor view's flags, so the app's own tick is unaffected by it. V-01 and V-08 are re-run at the close and `HeldInstalledPermissionsAppTest` keeps its token.

**3.5 Default, reduced motion, accessibility.** Sound is **on by default**: REQ-033's own ASSUMPTION and `GameSettings`' default. Reduced motion (REQ-023) concerns animation and does not change sound (D1). #Accessibility is an `idea`; the switch is a real `Role.Switch` with a state, so TalkBack reads it.

**3.6 How "with sound off, no action makes a sound or a haptic tick" is tested (rev 1, F1; DA-116).** REQ-033 A1 is tested **literally**: every action, **platform defaults included**. Two kinds of request are measured, each at a named point:
- **Our cues, at the output boundary:** requests reaching `SoundOut.play` and `HapticOut.tick`.
- **The platform's defaults, at the lever:** requests the Compose nodes make for the system click sound or a long-press haptic, which `PlatformFeedbackLever`'s providers intercept and count.
1. **JVM, `settings/src/test` (`FeedbackGateTest`, `REQ-033.A1`):** recording fakes; for each of the five events, sound off gives 0 sound and 0 tick; sound on gives exactly one sound, and a tick only for LOCK (**positive control**); a switch flipped between two events changes the next one at once.

**The lever: `PlatformFeedbackLever`** (one file, `app/src/main/.../PlatformFeedbackLever.kt`, the only place the names of rule 3 of the scan may appear):
- `@Composable fun Provide(content)` wraps the **whole** content of `TangramApp` (base, grid overlay, settings overlay): `CompositionLocalProvider(LocalSoundEffect provides SilentSoundEffect, LocalHapticFeedback provides SilentHaptic) { content() }`. Both locals are read by the nodes with `currentValueOf` (bytecode, rows 1 and 2), so the provider reaches every `clickable`, `combinedClickable` and `toggleable` in our tree without touching `browse`, `play` or `settings`. `LocalSoundEffect` is `@ExperimentalComposeUiApi`, so a BOM bump that removes or renames it is a compile error, not a silent regression.
- **The lever's precondition (rev 2, E1): no Dialog or Popup window in the release build.** The provider does **not** reach into a Dialog or Popup: every Compose window has its own `AndroidComposeView`, and `WrappedComposition` re-provides `LocalSoundEffect` and, through `ProvideCommonCompositionLocals`, `LocalHapticFeedback` at that window's root. (A click inside such a window would still be silent, because the ui flag makes that window's lazily computed `SoundEffect` a `NoSoundEffect`; a haptic there would **not** be suppressed.) The precondition holds because the REQ-008 A2 walk already forbids a dialog or popup root on every screen. The one accepted residue is the debug-only DevTools passcode Dialog (row 4).
- **`PlatformFeedbackLever.installProcessFlags()` (rev 2, E1)** sets `AndroidComposeUiFlags.isInteractionSoundEffectsEnabled = false` (row 3; it also makes the platform's own default `SoundEffect` the silent `NoSoundEffect`, a second layer under row 1). It is called **first in `MainActivity.onCreate`, before `setContent`**, so it precedes every `ComposeViewContext` and is not a side effect of composition (rev 1 set it in a `remember`). The lever file stays the only home of the name. `ComposeFoundationFlags.isInteractionSoundEffectOnClickEnabled` is **left at its default**, so the click request still reaches the lever's provider, which is what makes it countable.
- `SilentSoundEffect` and `SilentHaptic` are objects that do nothing but increment an `AtomicInteger` each (`interceptedClicks`, `interceptedHaptics`, `internal`): two bounded counters, the only test-visible state in `main`.
- **Why not `isSoundEffectsEnabled = false` / `isHapticFeedbackEnabled = false` on a view** (the orchestrator's first example): Compose binds `AndroidSoundEffect` and `PlatformHapticFeedback` to `ComposeViewContext.view`, the view-tree root found by `findViewTreeComposeViewRoot`, which under `ComponentActivity.setContent` is **the decor view**, a view the app can reach (rev 2, E2: rev 1 wrongly called it unreachable). So `decorView.isSoundEffectsEnabled = false` would silence the click. The provider is still the lever, for three reasons: (1) `isHapticFeedbackEnabled = false` on that view would **also silence our own lock tick**, because `ViewHapticOut` performs on the same decor view; (2) **a flag gives no positive control**, whereas the provider's counters show that each node asked and the lever answered; (3) the provider is **where every node reads** (rows 1, 2 and 4 all go through `currentValueOf`).
- **Covered by:** the scan (rule 3 keeps the names in this one file, rule 1 forbids `playSoundEffect` and `SoundEffectConstants` anywhere), `HeldPlatformFeedbackAppTest` (3.6 item 4), and **a mechanical V-08 check (rev 2, E3), not a manual duty**: V-08 reads the dex of the release and debug APKs it already builds, lists every caller of the platform sound and haptic APIs and fails on any caller outside a pinned allow-list (`V-08 FAIL feedback-caller …`). That covers a Compose BOM bump, a new library and our own code; only then does someone re-judge DA-125's inventory before extending the allow-list. The whole-APK caller set of the WO-006 close (not minified, the same BOM) is the allow-list (the V-1 row lists it).

### 5. Reset (REQ-034) *(item 5, DA-120, rev 1)*

- **Flow, in-screen, no Dialog:** the reset section shows `settings-reset` ("Reset all progress"). Tapping it calls `requestReset()`: the section shows the question and two full-width 48 dp buttons, **Keep** (`settings-reset-cancel`, first) and **Erase** (`settings-reset-confirm`). **Keep**, Back, closing the screen: `cancelReset()` / `close()`, nothing else (A2). **Erase**: `confirmReset()`.
- **`confirmReset()`:** `if (!confirmingReset) return` (a double tap erases once); `confirmingReset = false`; `store.resetAllProgress()`; `onReset()`. The store does what its KDoc says: every puzzle New, puzzle, best and play times erased, **settings and `lastShown` kept**. So **the sound setting is kept** (REQ-034 rule), proven with sound off.
- **After a confirmed reset the current puzzle stays shown, now New (rev 1, F3).** `onReset` is `BrowseController.afterReset()` = `showAt(indexState)`: a fresh `PlaySession` of the same puzzle restored from the store (all New, every piece in the tray); no `lastShown` write, no index change. The settings overlay stays open (the prototype's behaviour); the player closes it and sees the New board. The basis, weighed on the locked text:
  - **For "stay":** REQ-032's Statement says "WHEN it is closed, the game SHALL return to the same puzzle state": the same puzzle, now New, is the nearest reading, and F25 (G1, accepted, in CA-3) reads A1 as "…unless Reset all progress was confirmed" with the puzzle left open. It is the D2 option: the exact code `restart()` already runs, no new write.
  - **For "first" (the prototype loads puzzle 0; REQ-045 A1 opens a fresh install on the first puzzle):** REQ-045 A1 concerns a fresh *install*, which a reset is not (settings are kept); REQ-034's rationale ("hand a device to another player") is a rationale, not a Statement. No locked line requires the first puzzle, so nothing argues against "stay".
  - **Reversible in one line.** Offered to Jami as the two options (owner item 2). **I found no REQ reason against "stay": DA-120 chooses "stay" under row 12.**
- **Invariant, with a test: `afterReset` never calls `persist()`.** `open()` persists the leaving puzzle first; here persisting the live session would bring the erased state back. The invariant is stronger than "never call it" (rev 1, N3b): `persist()` captures `host.session`, which `showAt(indexState)` has **already replaced** with a New session, so even a late `onChanged` from the discarded session can only save the New board. A `browse` test seeds an in-progress live board, resets, calls `persist()` as `onPause` does, and asserts every puzzle is still New.
- **Atomicity and crash safety:** one atomic write (temp file + `ATOMIC_MOVE`, DA-47). A kill before the rename leaves the old document intact; after it, everything is erased: no half-reset. A disk failure never throws; memory stays erased and the next save or `sync()` (from `onStop`) retries.
- **Racing a save:** the store is main-thread only and synchronous, so a reset and a save cannot interleave. The stale session is covered by the invariant. A drag in flight cannot meet a reset (`open()` is refused while dragging and `inputEnabled` cancels a press, section 2).
- `DebugAids` state is not progress and is not reset.

## Risks & edge notes

- **Highest risk, for the Design Reviewer's spot-check: REQ-033 A1 completeness.** Rev 0 missed that the toolkit makes sound on its own. Rev 1 closes the known paths with the lever and measures them at named points, but "no other platform request exists" is an argument from the bytecode inventory of 3.7, not an observation: the platform's `playSoundEffect` has no external observer. What is left to attack: (1) a new Compose node type in a later BOM that asks for a sound or haptic by another route (V-08's feedback-caller check fails on any new caller, so a BOM bump cannot add one silently; `LocalSoundEffect` being `@ExperimentalComposeUiApi` makes a rename loud); (2) a Dialog or Popup window, which re-provides both locals and so escapes the provider (none exists in release; the REQ-008 A2 walk enforces it; the debug-only DevTools passcode Dialog is an accepted residue); (3) the gate bypass by a call path (the scan); (4) the real audio unobservable on a headless emulator (owner's phone). Honest limit: the click-sound lever is proven to intercept what the nodes ask; whether a given Android build adds a native click elsewhere is outside the app.
- **`AudioTrack` on the two channels.** Contract and smoke test of 3.3 and 3.6 item 5. Fallback: a short-lived per-play `MODE_STATIC` track from the in-memory PCM (no file). An emulator with no audio output fails the preflight unless a named waiver exists; the seam tests are what gate REQ-033 A1, the smoke is what gates "the output works at all".
- **Haptic observability.** A request count only. `performHapticFeedback` needs the window attached and follows the system touch-feedback setting. The ViewModel holds a `WeakReference` to the decor view.
- **First-sound latency.** The five tracks are built on a background thread at start; a sound requested before that is dropped silently.
- **Reset racing a save.** Single-threaded stores, idempotent `confirmReset`, the no-persist invariant resting on `persist()` reading `host.session` (section 5). Reviewer's second target: `BrowseController.afterReset` is the only reload.
- **A press under the overlay.** Handled by `inputEnabled` (the gesture machine is cancelled through the existing path). **Keyboard focus under the overlay:** `onEnter = { cancelFocusChange() }` on the base group plus `clearFocus()` on open (rev 2, E4); the scaffolding test pre-focuses ‹, opens the overlay, then sends Tab and Enter.
- **The ⚙ size.** 48 dp (DA-53). At 360 dp in Finnish the title ellipsizes sooner; the WO-006 no-clip walk reads `puzzle-state` and `puzzle-counter` (contingency: `browse` top bar weights, never a loosened test).
- **API 26.** No version branch in the code. The settings walk and the touch matrix run on both channels; `svc wifi` stays killed on that image, so C7 on API 26 is "flag set and data cut".
- **The settings sheet scrolls.** On `PHONE_360x780` with Finnish and font scale 2.0 the privacy text is below the fold; the tests `performScrollTo` and assert it displayed. REQ-035's "no scrolling" is about the tray.
- **Release safety.** `FeedbackProbe` is debug-only (V-08 denies it in release, requires it in debug); the release `DebugAids` twin only passes through (asserted); `PlatformFeedbackLever` is in `main` and ships (its two counters are bounded ints); no permission element; no new library; `settings` has no manifest; `ReleaseSeparationTest`'s module list and `a4FileSetS` both gain `settings`.
- **Promise word list.** The how-to and every label are scanned; the drafts were read against the lists by hand. A hit is fixed in the text, never by loosening a stem.
- **Owner-checkpoint items (Jami):** (1) the tones: loudness, character, whether the lock tick can be felt; (2) **after a reset: the current puzzle stays, now New (the design), or the first puzzle**; (3) the Finnish how-to and the reset question's wording (F14 already covers the note, the privacy text and the prototype labels); (4) the ⚙ at 48 dp (DA-53 already ruled it); (5) **Android's own touch click sounds and the long-press vibration on › are now always off, whatever the sound switch says** (Compose plays them by default; no REQ asks for them).
- **The v1 save format.** Unchanged; tests seed stored states through the existing store only.
