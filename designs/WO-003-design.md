# Design — WO-003 · rest of #Solving: the first playable build

**Author:** Design Author  ·  **Date:** 2026-10-02  ·  **Status:** Revised after design review (F1-F7, N1-N8)  ·  **Baseline:** architecture.md v1.0, build-map v1.1, req_types v0.2, decisions.md (to 2026-10-02)

## Scope

- **Implements:** REQ-002 A1–A2, REQ-011 A1–A2, REQ-012 A1–A2, REQ-013 A1–A3, REQ-014 A1–A2, REQ-015 A1–A2, REQ-016 A1–A2, REQ-017 A1–A2, REQ-018 A1–A3, REQ-022 A1, REQ-023 A1–A2, REQ-043 A1–A2. TYPE-006 (the two transitions this WO needs) and TYPE-007 in the kernel. Minimal `app` shell (edge-to-edge, F3 policy, layout class, tray rows of REQ-035/036; their acceptance stays WO-006).
- **Carried in, closed here:** REQ-020 A2; REQ-021 and REQ-051 on screen; F5/DA-5 (interrupted drag); the "last displayed preview" calling rule; WO-001 code review F3 (ConvexClip fail-closed) and F8 (`overBoard`); REQ-039 A1 and REQ-045 A2 on screen; the on-device library check; the release-APK `tangrams/` check; path-data `d` validation (WO-002 N9); the API 26–32 release launch check; the 180 ms glides (WO-001 carry-out).
- **Governed interfaces:** `IPuzzleLibrary` (consumes, unchanged). `IProgressStore` none. **No `I*` change, no `kernel.model` file edited, `contracts/` untouched.** Nothing here needs a contract delta.
- **Hard-stop domains touched:** none. The manifest is not edited (see section 8, the activity keeps its attributes). No dependency adds network, permission, ads or analytics; the only new libraries are allowlisted test libraries (section 9).
- **Not designed here (so nobody builds it silently):** browsing, Restart/Retry/Next, solved bar (REQ-024..026, 050 → WO-004); saving (WO-004); sounds and haptics and the O-06 callbacks (DA-27; → WO-007/008); timer slot and DevTools slot (O-09 slots arrive with their consumers, WO-005/008); tablet acceptance and language acceptance (WO-006).

## Chosen design

### 0. Shape in one picture

```
app  (O-05, O-09)   MainActivity ─ edge-to-edge, orientation policy (F3), reduced-motion probe
 │                  AppViewModel ─ PuzzleLibrary.packaged() → first puzzle → PlaySession (survives rotation)
 │                  TangramApp   ─ paper background · safe-drawing insets · title bar placeholder · tray rows per LayoutClass
 ▼ wires
play (#Solving)     PlayArea(session, layoutClass, trayRows, screenHeight)   ← the only composable app calls
 │                    ├─ PlayLayout        pure geometry: board scale/origin, tray scale, cells        (REQ-013, 035/036)
 │                    ├─ PlaySession       the one puzzle's state + intents + animation clock          (REQ-012, 014..018, 022)
 │                    ├─ GestureMachine    pure pointer-event → session intents; HitTest               (REQ-014..018, F5, F13)
 │                    ├─ draw/*            Canvas drawing of silhouette, pieces, preview, pulse, picture, confetti
 │                    └─ DropResolver      (WO-001) + refit() for tap-turn / flip on the board          (O-01)
 ▼
kernel              LockSearch (O-01) · PieceGeometry (+ centroid helpers) · Silhouette · NEW: SolvedCheck, PuzzleStates,
                    LayoutRules, TrayRules (TYPE-001 resting turn + colours)
content / contracts unchanged
```

Everything that decides something is **pure Kotlin with no Compose or Android type**, so it runs in `play/src/test` on the JVM: layout, session, gesture machine, hit test, twist maths, timeline, path-data parser. Compose is only the drawing and a ~30-line adapter that turns `PointerInputChange` into `GestureMachine` calls. This is the main way the design keeps the emulator out of the critical path (section 10).

### 1. Screen composition (O-09, O-05, decisions F3, TYPE-007, REQ-035/036)

**`app` owns** (REQ-035/036 "edge to edge, insets, back button, rows"):
- `MainActivity`: `enableEdgeToEdge(SystemBarStyle.light(TRANSPARENT, TRANSPARENT))` (the paper background is light, so dark bar icons); sets `requestedOrientation = PORTRAIT` when `LayoutRules.lockPortrait(Resources.getSystem().configuration.smallestScreenWidthDp)` (device-level value, decisions F3) and `UNSPECIFIED` otherwise; re-evaluated in `onCreate`, which runs again after every recreation (no `configChanges` in the manifest, DA-26). Back: no handler, so Android leaves the app (no overlay exists yet; REQ-035 rule, state saved from WO-004).
- `TangramApp` (composable; window size from `LocalWindowInfo.containerSize` / window metrics **including the bars**, so a phone gets the same tray on API 26 and API 37; `Configuration.screenHeightDp` is not used, N3): `Box(paper background, fillMaxSize)` behind the system bars, then a `Column` with `windowInsetsPadding(WindowInsets.safeDrawing)`: **title bar placeholder** (66 dp compact / 74 dp tablet, one `BasicText` with `puzzle.title.inLanguage(language)`, REQ-012 rule "title in the game's language"; `browse` replaces it in WO-004) and `PlayArea(Modifier.weight(1f))`. Safe-drawing padding keeps the tray clear of the gesture bar and cutouts (REQ-035 A2).
- `LayoutClass` = `LayoutRules.classFor(windowWidthDp)` from the same window metrics; **tray rows** = `TrayRows.forClass(cls)`: PHONE `[[LT1,LT2,MT],[SQ,PG,ST1,ST2]]`, TABLET `[[LT1,LT2,MT,SQ,PG,ST1,ST2]]` (REQ-035/036 rules; the *full-set* rows, `play` drops pieces the puzzle lacks and empty rows, REQ-045).
- Reduced motion: `reducedMotion = { !ValueAnimator.areAnimatorsEnabled() }` (API 26, decisions F9), passed down as a lambda read at event time.
- `AppViewModel` (`androidx.lifecycle.ViewModel`, already on the classpath via activity): holds `PuzzleLibrary.packaged()` and the `PlaySession` so rotation / window change / split-screen keeps every piece without any manifest change (decisions F3 "any window change keeps every piece"). On `onCreate` it calls `session.interruptDrag()` (idempotent) (F5: window change).
- `onPause` calls `session.interruptDrag()` (F5: app hidden).

**`play` exposes** exactly one composable and one state holder:

```kotlin
class PlaySession(val puzzle: Puzzle, reducedMotion: () -> Boolean = { false },
                  resolver: DropResolver = DropResolver(puzzle)) {
    val state: PuzzleState          // TYPE-006, observable
    val isDragging: Boolean         // O-09 / F5: app uses it to make other controls ignore touches (none exist yet)
    fun interruptDrag()             // F5/DA-5: restore the whole pick-up pose, silently
}
@Composable fun PlayArea(session: PlaySession, layoutClass: LayoutClass, trayRows: List<List<PieceId>>,
                         screenHeight: Dp, modifier: Modifier = Modifier)
```
Everything else in `play` is `internal` (except the public `BoardTransform` semantics key, section Test seams) (visible to `play/src/test` and `play/src/androidTest`). `play` reads the language from nothing (no strings of puzzles), only its own string resources (section 7).

**`app` wires `content` → `play`:** `AppViewModel` calls `PuzzleLibrary.packaged()` (the concrete `content` class; app may depend on `content`, G-06) and opens **`library.puzzles.first()`**, which is the rating-1 mini puzzle `shapes-mini-1` (REQ-045 A1 on screen is WO-004's, but this is already what a fresh install shows). **Debug-only testing aid (DA-23, review F6):** a `puzzle` string extra selects another packaged puzzle so Jami can see the full-set tray, the L/M marks, the flip badge and LT/MT twists (`shapes-mini-1` has only SQ/ST1/ST2). It is read in `app/src/debug` (`PuzzleExtra.read(intent): String?` = `runCatching { intent.getStringExtra("puzzle") }.getOrNull()`; unknown id gives the first puzzle) with a release twin in `app/src/release` that returns `null` (the ADR-006 source-set pair), so the exported launcher in release never reads an extra. It is a verification-channel aid, not a feature, and not DevTools. Jami gets `adb shell am start -n io.github.jamisuni.tangram/.MainActivity --es puzzle <id>` lines at the checkpoint; WO-004 retires it or keeps it debug-only.

### 2. Coordinates and the board (REQ-011, REQ-023, REQ-039, REQ-021, REQ-051, G-03)

`PlayLayout` (pure; all lengths in **dp**, `Double`) is computed from the `BoxWithConstraints` size of `PlayArea`, `screenHeight`, `LayoutClass`, `trayRows`, the puzzle's piece set and the silhouette bounds. It ports the prototype's `layout()` (DI-1/DI-2 §3) with the REQ numbers:

- Tray: side margin 8 / 16 dp, cell gap 8 / 14 dp (PHONE / TABLET), bottom margin 10 / 14 dp, cell padding 12 dp (REQ-013 ASSUMPTION). Turn diameter `d = 2 × max centre-to-corner` of the shape from `PieceGeometry` (derived once: LT 4.22, PG 3.16, MT 2.98, ST 2.11, SQ 2.00, a test pins it against the REQ-013 table). **Tray scale `ts`** = the largest `s` at which every row of the **full set** fits `trayWidth − gap·(n+1) − 12·n ≥ s·Σd` and every row height `≤ max(84, 0.16·screenHeight)` dp (REQ-013 rules; same for every puzzle, so A3 holds by construction). Cell width `= d·ts + 12`, row height `= (largest d in the row)·ts + 12`, rows of the puzzle only (empty row dropped, remaining rows centred).
- **Board scale `dpPerUnit`** = `min(boardW·0.82/silW, boardH·0.80/silH)` (the "about 10 % padding" of REQ-035; prototype values), origin so the silhouette bounding box is centred. `toDp(u) = origin + u·dpPerUnit`, `toUnits` is its inverse. **`dpPerUnit` is the value passed to `LockSearch.lockDistance` (O-01, TYPE-004)** by every caller; nothing else computes R.
- **Board rect** = the area between the top of `PlayArea` and the tray top (minus 8 / 12 dp). **`overBoard` (WO-001 F8, DA-15):** true iff the dragged piece's *floating centre* (not the finger) lies in the board rect grown by 20 dp on the left, right and top and ending 4 dp above the tray top (prototype `inBoard`). It decides three things only: whether a preview is searched, whether a release searches, whether a mini puzzle may pulse. Dropping with the centre above the tray top but outside the 20 dp margin, or on the tray, is a plain go-home (REQ-020; DA-4: no pulse).

**Drawing (Compose `Canvas`, `play.draw`).** All piece polygons are drawn from `PieceGeometry.offsets(shape, turn, mirrored)` minus the centroid, times the scale, around a centre — **no `rotate`/`scale(-1,1)` canvas transforms**, so the TYPE-003 convention exists once (kernel) and can never drift on screen. Layer order: board background (white, rounded) → **silhouette** → tray → placed pieces (2 dp white edge) → **preview** → corner pulse → dragged / gliding piece → picture (when solved) → confetti.
- **Silhouette (REQ-011):** the solution polygons mapped through `toDp`, merged into **one** `androidx.compose.ui.graphics.Path` by `Path.op(Union)` and filled in one flat colour `#4A4E69`. One path means no inner edge and no anti-aliasing seam (A1); the path's vertices are the mapped solution corners, so the outline is exact (A2). If an `op` returns `false`, the silhouette falls back to the per-polygon fill (G-10: draw something, never crash); the A1 pixel test would fail loudly on every shipped puzzle if this ever happened on a device, so the fallback cannot hide a regression.
- **Placed pieces:** fill in the TYPE-001 colour (from `TrayRules`), 2 dp white edge. **Dragged piece:** same, scale `lerp(startScale, dpPerUnit, ease(min(1, elapsed/120 ms)))` (REQ-014: 120 ms growth, then exactly `dpPerUnit`; never above it).
- **Landing preview (REQ-021, DA-20):** `drawPath(style = Stroke(2.5.dp, pathEffect = dash(7 dp, 5 dp)))` in white, no fill (the REQ asks for an outline), only when `frame.preview != null`.
- **Corner pulse (REQ-051, DA-20):** for each `CornerPulse.corners` a circle r = 9 dp in the accent `#3D8BFD` with a 2.5 dp white ring, alive 600 ms from the `Home` that carried it; animated as radius × (0.6 → 1.3 → 1.0); with reduced motion drawn static for the same 600 ms. Only corners, never a piece position (`CornerPulse` carries nothing else).
- **Solved picture (REQ-023, REQ-039):** drawn in a `Canvas` with `Modifier.graphicsLayer { alpha = a }`, `a = SolvedTimeline.pictureAlpha(now − t0)`: **0 until 600 ms, linear to 1 at 1400 ms** (reduced motion does not change this: "the picture still appears"). Inside `clipPath(silhouettePath)` (the *same* `Path` object as the silhouette fill, so A1 "outline identical" is structural): fill `picture.base`, then each `PictureShape` in order, units → dp through the board transform, stroke width `width × dpPerUnit` (default 0.05 units when a stroke has no width, prototype), `opacity` multiplies the colours' alpha, round caps and joins. `Path` shapes go through `PathData.parse(d)` (below). Pieces are drawn under the picture and **stop being drawn once `pictureAlpha == 1`** (their 2 dp edge is centred on the outline and would show 1 dp outside it; A2: no piece boundary visible). The flip badge disappears when solved.
- **Pop and confetti (REQ-023, DA-19):** unless reduced motion, from `t0`: pieces scale 1 → 1.06 → 1 about their centres over 300 ms, and 110 confetti rectangles for 2.4 s from the board's centre; particle paths are closed-form ballistic functions of time from a **fixed-seed** generator (`Confetti.at(t)`), nothing is drawn after 2400 ms. Reduced motion: neither. The sound is WO-007.
- **Path data (WO-002 N9, G-10, DA-21):** `PathData.parse(d): List<PathSeg>?` accepts: absolute `M L Q C Z` only, first command `M`; letters may be glued to numbers (`M3.3,3.35 Q3.7,3.55 4,3.35` is valid); each command takes exactly its arity of numbers, **implicit command repetition is rejected**; number token = optional `-`, digits with optional `.digits` (or `.digits`), **no exponent, no leading `+`**; separators = runs of spaces and/or one comma; all finite. Anything else (unknown letter, lower case, wrong count, NaN/Infinity, empty) returns `null` and **that one shape is skipped**, the rest of the picture still draws. It is *not* made a parse error in `content` (a decoration must not remove a playable puzzle at run time); instead a build test parses every `d` in every packaged puzzle and requires non-null, so a bad file cannot ship (REQ-039). Pure Kotlin, JVM-tested.

### 3. The tray (REQ-012, REQ-013, REQ-043, REQ-018, decisions F2)

- `TrayRules` (kernel, TYPE-001): order `PieceId.entries`, **resting turn** per shape (LT 4, MT 1, ST 4, SQ 1, PG 0 — prototype `STANDARD_TURN`, unmirrored) and the seven colours. `PlaySession` starts every piece in the tray with that turn, unmirrored; a piece sent home **keeps the turn and mirror it had** (F2); Restart/Retry reset are WO-004.
- A cell is drawn on the tray `Canvas`: rounded cell, the piece centred at the cell centre at scale `ts` in its current turn/mirror (cell size never depends on turn, A2), or, if the piece is not in the tray, only its **dashed outline** in the resting pose (REQ-012 rule, REQ-043 A2).
- **Size marks (REQ-043)** and the **flip badge (REQ-018)** are real composables over the canvas so that they have semantics: a `BasicText("S"|"M"|"L")` chip in the cell's top-left corner, tinted with the piece colour, **present in the tree only while the piece is in the tray** (`testTag("size-mark-<id>")`; the letters come from string resources that are identical in both languages, REQ-047); on SQ and PG nothing. The badge is a transparent **60 × 60 dp** `Box` (`testTag("flip-badge")`, role Button, `contentDescription` from string resources, with a 38 dp visible disc drawn inside it; it carries **no pointer handler and no semantics `onClick`** (one touch path only: `HitTest`, section 4; tests use `performTouchInput`, never `performClick`; role and `contentDescription` stay for tests and TalkBack labelling, N6a). Tray cells are drawn on the Canvas and have no nodes; tests find cells through `PlayLayout.cell`.
- Badge position **(review F4)**: tray = a 60 dp square whose right edge is the PG cell's right edge plus the adjacent gap and whose top is the cell top, **never extending past the PG cell's own column** (it covers none of ST1's cell, the S mark, or LT2's cell; it may overlap PG's own cell, where the intent is PG-related anyway); visible disc 38 dp at its top-right; at 390x844 the square stays inside x 106.95-211.65. On the board the badge-wins-overlap with neighbouring pieces is F13 as decided and accepted. Board: right of the parallelogram's bounding box (+22 dp) and 4 dp above its top, **clamped inside `PlayArea`**; hidden while PG is dragged, and when solved. Present in every puzzle that contains PG, never elsewhere (REQ-018 A2).
- Tray tap-turn: `+1` step on the stored `Turn` (centre fixed, TYPE-003); tray flip toggles `mirrored`. Both instantly and without effect on `PuzzleState` (TYPE-006).

### 4. Gestures (REQ-014..018, decisions F5/F13, DA-5)

One `pointerInput` on the whole `PlayArea` (board **and** tray share one surface, because a drag crosses between them) implemented with `awaitEachGesture`. It does nothing but translate events: `down/move/up(id, positionDp, timeMs)` → `GestureMachine`, **Adapter contract (review F1: a system cancel is NOT a coroutine cancellation).** Compose delivers `ACTION_CANCEL` as an ordinary event in which every pressed pointer goes up with the change **already consumed** (`onCancelPointerInput`); the coroutine keeps running. So: read changes in the **Main** pass; call `up` only for `changedToUp()` (`previousPressed && !pressed && !isConsumed`); a pointer that goes up **consumed** calls `machine.cancel()`; never use `changedToUpIgnoreConsumed()` or `!pressed` for release; keep `finally { machine.cancel() }` only for node detach / key restart. A cancel while `Pressed` is **not a tap**. Pointer positions are converted px to **dp in the adapter** (all machine thresholds are dp) and **every** pointer id is forwarded (second finger = twist). The machine is pure and holds the only gesture state:

| State | Entered by | Leaves by |
|---|---|---|
| `Idle` | start, any end | `down` on a target |
| `Ignored(ids)` | a badge hit, or any `down` while not `Idle` that is not the twist candidate (second finger while only `Pressed`, third finger, a finger that survives an external interrupt) | each id is dropped when it lifts or on `cancel()`; no effect on the session. Two pieces can never be pressed at once |
| `Pressed(piece, id, start)` | `down` whose `HitTest.pick` is a piece; (a badge hit acts immediately on `down`: `session.flip…`, then `Ignored(id)` until that finger lifts) | displacement from `start` ≥ 12 dp → `Dragging` (DA-16: sticky; once past 12 dp it is a drag even if the finger returns) · `up` with displacement < 12 dp → **tap** (any duration, REQ-015 A1) |
| `Dragging(id, twist?)` | `session.beginDrag(...)` | **unconsumed** `up` of the drag finger → `session.release`; `cancel()` → `session.interruptDrag()`; if `session.isDragging` / a drag-generation counter shows an external interrupt (`onPause`, size change, `onCreate`), the finger becomes `Ignored` on its next event (review F3d) |

- **Hit test (REQ-015, F13)** `HitTest.pick(p, layout, session)`: (1) the flip badge's 60 dp square; (2) a **board** piece whose polygon contains `p`; (3) otherwise the board piece with the **nearest edge within 12 dp** (so a touch 10 dp outside a small triangle picks it up, A2); (4) a **tray** piece whose cell contains `p`. A badge hit always wins; while dragging, `pick` is not consulted for new touches. Solved → nothing is hit.
- **Drag (REQ-014, DA-17):** at the 12 dp crossing `beginDrag(piece, finger, nowMs)` records the **pick-up pose** (`Tray` or `Board(at)`, turn, mirror) and sets the piece to `Dragged`. A tray drag from `NEW` runs `PuzzleStates.onTrayDragStarted` (TYPE-006, O-07). **Floating:** the piece centre is `finger + (0, −lift)` with `lift = (largest y of the centred shape **at the pick-up turn**)·dpPerUnit + 30 dp` (PHONE) / `40 dp` (TABLET), **fixed at drag start** (a twist turns the piece about its fixed centre, TYPE-003; the lowest point may then sit under 30 dp above the finger, accepted, owner's eyes), applied to tray **and** board pieces; board pieces also re-centre horizontally on the finger, a sideways jump of up to ~100 dp for a large triangle grabbed at a corner, eased over the same 120 ms (logged in DA-17); position and scale ease from the pick-up values to the floating values over 120 ms (`DragMotion`, pure). After 120 ms the centre equals `finger + offset` exactly: no smoothing, no lag (A1; F12 frame-level).
- **Frame sync (REQ-021 rule, WO-001 calling rule 1):** the finger writes `drag.finger` immediately; **once per frame** `session.onFrame(nowMs)` (from `withFrameNanos`; **one time base and one loop for the whole drag**: the loop runs every frame while `drag != null`, also when the finger is still, and animation starts are stamped with the frame-clock time, never the pointer `uptimeMillis`, so Compose test clocks and devices agree, N2) freezes `drag.frame = DragFrame(pose, preview)` where `pose` is the `DragPose` of this frame and `preview = resolver.preview(pose, placed, dpPerUnit)`; the piece is drawn at `frame.pose` and the dashed outline from `frame.preview`. **`release` uses `frame.pose`, never the live finger**, so the drop locks exactly where the last *displayed* preview was (A1). A release before the first frame of a drag uses the pose of the drag start (preview was never displayed → search from that pose).
- **Twist (REQ-017, DA-18):** a second `down` while `Dragging` and no twist finger is active (a new twist after the first twist finger lifted **is** allowed; a second finger down while only `Pressed` is `Ignored`, not promoted; an already-down third finger is never promoted) records `a0 = atan2(second − first)`; each later move of either finger adds the **shortest signed angle change** to a cumulative angle (continuous, so twists past 180° keep counting); `steps = sign(a)·ceil((|a| − 22.5°)/45°)` for `|a| > 22.5°`, else 0: strict "passes", symmetric, so exactly ±22.5° gives 0 and just beyond gives ±1 (review F3e); angle changes are not counted while the fingers are closer than 24 dp (jitter, N2), but the reference angle keeps updating so crossing back over 24 dp injects no skipped rotation (N9, DA-31); the piece turn is `turnAtTwistStart + steps` applied about its **centre** (`session.setDragTurn`). A 90° twist = 2 steps, a 20° twist = 0 (A1/A2). Lifting the second finger keeps the turn and the drag goes on; lifting the **drag** finger ends the drag (release), whatever the second finger does; a third finger is ignored. Positive angle (clockwise on a y-down screen) = positive `Turn`, as TYPE-003.
- **Tap (REQ-016):** tray piece → `tapTray` (+1 step). Board piece → `tapBoard`: `DropResolver.refit(current, turn + 1, mirrored, placed, dpPerUnit)` — **the new `play` function over the same `LockSearch.find` (O-01)**, with the float origin that keeps the piece's centre (`PieceGeometry.originKeepingCentre`, new kernel helper). Found → the piece gets the returned `at` and the new turn (it may shift to the lock, as the prototype); `null` → nothing changes and `shake` starts (A2: "no room to turn keeps position and turn"). The piece is still *in* `placed` for the search but is filtered by its own id inside `find` (F31), so it never blocks itself.
- **Mirror (REQ-018):** the badge calls the same two functions with `mirrored = !mirrored` (`flipTray` / `flipBoard` → `refit`). The search never tries the other mirror image by itself (it is given exactly one), so A3 follows from TYPE-004.
- **No crash path (G-10):** every session intent without a drag (`release`, `dragTo`, `setDragTurn`) is a **no-op** (`release` returns `DropOutcome?`, null when no drag); `interruptDrag` is idempotent.
- **Release (REQ-019/020):** `resolver.release(frame.pose, placed, dpPerUnit)` → `Locked(placed)`: the session stores the exact `at`, runs `SolvedCheck`/`PuzzleStates.onPieceLocked`; `Home(piece, turn, mirrored, pulse)`: the piece goes to its tray cell **with that turn and mirror** (F2), `pulse` (if any) starts the corner pulse. Both start a **180 ms glide**: the *logical* location changes at once (REQ-012 A2: a piece is always tray, board or dragged), the glide is a cosmetic `Glide(from centre/scale, startMs)` drawn until 180 ms. No sound, **no message of any kind** (REQ-020 A2: `DropOutcome` has no message field and the UI has no text node for it).
- **Interruption (F5/DA-5):** `interruptDrag()`, called by `cancel()` (a system cancel = consumed up, see the adapter contract), `onPause`, `onCreate` after recreation, and by `PlayArea` when its layout size changes mid-drag — **never calls `preview` or `release`**; it restores the *whole* pick-up pose (cell, or board `at`, with the turn and mirror taken at pick-up, discarding any twist), clears the frame and the twist, starts no pulse, no glide, no sound, and does not undo `NEW → IN_PROGRESS` (the drag did start, TYPE-006).
- **While dragging, other controls ignore touches (F5):** `session.isDragging` for `app` (kept although nothing consumes it yet: O-09 names it, and it is the machine's external-interrupt check; N6b); inside `play` the badge is inert and a second finger is only a twist.

### 5. Game state for one puzzle (TYPE-006, REQ-022, O-01, O-07)

`PlaySession` (play, plain Kotlin class, fields are Compose `mutableStateOf` so drawing observes them; no coroutines, no clock of its own: time comes in through `onFrame(nowMs)` and the intents' `nowMs`, all **frame-clock** time, never pointer uptime):

- `pieces: List<PieceState>` for exactly the puzzle's pieces in TYPE-001 order (mini = its own; REQ-045), `PieceState(piece, turn, mirrored, where)` with `where = Tray | Board(at: ExactPoint) | Dragged`. `placed` = the `Board` ones as `PlacedPiece`s.
- `state: PuzzleState` through the kernel: `PuzzleStates.onTrayDragStarted(s)` (NEW → IN_PROGRESS, else unchanged) and `PuzzleStates.onPieceLocked(s, allLocked)` (IN_PROGRESS → SOLVED when `allLocked`; SOLVED never leaves in this WO). `allLocked = SolvedCheck.isSolved(puzzle pieces, placed)` = every piece of the puzzle has a `Board` entry — **no comparison with the stored solution** (REQ-022).
- `drag: DragState?`, `pulse: Pulse?`, `glides`, `shake`, `solved: SolvedAt(t0, reduced)?` — the animation facts, each a start time plus constants in one `PlayTiming` object (glide 180, grow 120, pulse 600, picture delay 600, fade 800, confetti 2400, pop 300, shake 400 ms). Pure functions of `(now − start)` (`SolvedTimeline.pictureAlpha`, `Confetti.at`, `shakeOffset`, `pulseRadius`) are the JVM-testable timeline.
- No persistence (WO-004). The `ViewModel` keeps the session across rotation; a killed process starts the puzzle fresh.

### 6. Carried engineering items

1. **ConvexClip fail-closed (WO-001 F3).** Today non-finite input makes `intersectionArea` return 0 — for the *inside* test that is "outside" (closed) but for the *overlap* test it is "no overlap" (**open**). The fix sits where both uses are combined, keeping `fitAt`'s signature and behaviour (`LockMarginTest`, `LockSearchTest` call it) and making `misfit` its body; real callers cannot produce non-finite values (`Rational` is Long-based), so this is defence in depth: `LockSearch.fitAt` is split into a pure `internal fun misfit(subject, silhouette, others, area): Fit` over `Vec2` lists; it returns `Fit(+∞, +∞)` (invalid under both tests) when any coordinate of any input polygon is non-finite or any area result is non-finite. `ConvexClip` keeps "never NaN" (documented 0). Kernel test: NaN/∞ in subject, in a silhouette polygon and in a placed polygon each give "no lock". (DA-25; the rationale is defence in depth, not "no single return value".)
2. **On-device library check (WO-002 F1).** `rejected` stays `internal`; no public read and no contract change. The check is changed to an equivalent one: `app/src/androidTest` (the APK Jami installs) reads the classpath `tangrams/index.txt` (the same resource `PackagedPuzzles` reads) and asserts `PuzzleLibrary.packaged().puzzles.map { it.id.value }.toSet() == index stems` and `size == line count`. A rejected file would be missing from `puzzles`, so "count = index lines" **is** "rejected is empty" (DA-22). Runs on the API 37 and, when present, the API 26 image (section 10). Plus, on device (`play/src/androidTest`), a **kernel smoke**: for every packaged puzzle, `DropResolver.release` locks every solution piece (`poseOf` + a greedy order) → `SolvedCheck` true — it proves the JVM modules (BigDecimal, `Math.hypot`, Java-17 bytecode) work on API 26, where an API-level slip would otherwise appear only in the owner's hands.
3. **Release-APK `tangrams/` check (WO-002 F4).** `tools/check_apk_puzzles.py` (stdlib, with a self-test that corrupts a copy and must fail, like the V-verifiers): runs `:app:assembleRelease`, unzips, requires `tangrams/*.json` and `tangrams/index.txt` to equal `Tangrams/*.json` (non-schema, byte for byte) and the index. It lives in `tools/` (not `.swdev/verifiers/`, so `architecture.md` §2 needs no new row); **Carried to WO-005 (WO file / build-map row): fold it into V-04's APK scan**, so the G-08 check does not rot. ### 10. Verification channels (G3) and the emulator / Robolectric decision (G-02)

**Chosen: Compose UI tests on the emulator via `connectedDebugAndroidTest`; no Robolectric.** Reasons: (a) three acceptance IDs are about *pixels* (REQ-011 A1 no seam, REQ-039 A1 nothing outside the outline, REQ-023 A2 no piece boundary) and Robolectric's native-graphics mode is the least trustworthy place to assert them, with API-37 support lagging; (b) the emulator is already installed and architecture §5 names it as a channel; (c) no new test library beyond the allowlisted AndroidX ones, so G-02 needs only a version row. Cost: UI tests are not in `gradlew test`; **Test & Verify must run `assembleDebug test connectedDebugAndroidTest`** on the API 37 AVD, and the instrumented suite plus the library/kernel smoke again on the API 26 AVD **when present, else the recorded waiver** (the instrumented channel is proven on the API 37 emulator in a scratch copy; the API 26 image is pending from Jami). To keep that cost small the design puts logic in pure classes (JVM) and keeps the instrumented set small: pixel tests (silhouette seams, picture clip, no piece boundary, preview, pulse, confetti end), semantics tests (tags, 60 dp badge bounds, size marks, no error text), one real-touch end-to-end drag/solve of the mini puzzle in `app`, the library check and the kernel smoke.

## Alternatives considered

| Alternative | Why not chosen |
|---|---|
| **One `pointerInput` + pure `GestureMachine`** (chosen) vs per-piece `draggable` / `detectDragGestures` / `transformable` modifiers | Per-piece modifiers cannot do a drag that crosses tray → board, the second-finger twist, F13's "inside, else nearest edge within 12 dp, badge wins", or the F5 whole-pose restore, and each would hold its own copy of the gesture state. One surface = one state machine = JVM-testable with scripted traces. |
| Pieces as composables with `graphicsLayer { rotationZ; scaleX = -1 }` | Gives per-piece semantics nodes but re-implements TYPE-003 (turn/mirror order, clockwise sign) in the UI; a mismatch with the kernel would put the drawn piece away from where the lock puts it. Canvas from `PieceGeometry.offsets` has one convention. Tests read session state and pixels instead. |
| Silhouette as per-polygon fills with a same-colour hairline stroke (prototype) | The stroke grows the outline outward by half its width, so "matches the solution outline exactly" (REQ-011 A2) would be approximate. `Path.op(Union)` is exact and seamless; the pixel test proves it per puzzle. |
| Robolectric for Compose UI tests | See section 10. |
| `PuzzleLibrary.rejected` made public (WO-002 F1 option 1) | A public read for one test; the equivalent count check needs no API. |
| `configChanges` in the manifest so rotation never recreates the activity | Needs a manifest edit (V-01 re-proof) and fails *open* (an unlisted change loses the game); the ViewModel fails safe. |
| `overBoard` from the finger position | A lifted piece (≥ 30 dp above the finger) near the silhouette's bottom would need the finger inside the tray to be placed. Centre-based is the prototype's tested behaviour (DA-15). |
| Tray rows decided in `play` | REQ-035/036 are #Layout (code home `app`, build-map); `play` still owns the scale and cells, as REQ-013 is #Tray. |
| Reducer / immutable state flow for `PlaySession` | More code for no extra testability here: the session is plain Kotlin and its intents are synchronous. |
| Build `PlayEvents` (O-06 callbacks) now | No consumer until WO-007 (sound) and WO-008 (time); an interface with no caller is a D3/D4 violation. `PlaySession` is the single place the events will be raised from (`beginDrag`, `tap*`, `release`), so adding them later touches one class. |
| **Split into two WOs** | See "Suggested cut". |

## Risks & edge notes

- **Highest risk (flag for the Design Reviewer): the drag session — `GestureMachine` + frame-synchronised preview/release + interruption.** It combines multi-touch, a state machine, frame timing, F5 restore and the O-01 calling rules, and its failures are silent on the JVM and visible only on a finger (the owner has never played this on a phone). Mitigations: it is pure and exercised by scripted traces including cancel, second-finger and lift-order cases; release is *defined* on `frame.pose`; one real-touch instrumented path; the owner's eyes (governance row 9). Read sections 4 and 5 first.
- **Second: Compose pixel behaviour** (the `Path.op` union seam, clip edge bleed, the 2 dp piece edge outside the outline) — covered by per-puzzle pixel tests, but they run only on the emulator.
- **Third: the channel** — proven on the API 37 emulator in a scratch copy (a trivial `androidTest`); still open: the API 26 image (Jami; else a recorded waiver) and `ui-test-manifest` in the real `play` module, so the first Compose task starts only after the channel runs in the repo.
- **Edge-swipe conflicts:** with gesture navigation a drag that starts near a screen edge can trigger system back. Tray side margin is 8 dp; if the owner reports it, add `Modifier.systemGestureExclusion()` on `PlayArea` (no REQ forces it now).
- **Never crash on touch (G-10):** `GestureMachine` ignores unknown pointer ids and events after `cancel`; `LockSearch` already returns `null` for NaN/∞; `PathData` returns `null`; `Path.op` failure falls back; `PuzzleLibrary.packaged()` failing is a packaging defect that stops the app at launch by design (DA-10) and is guarded by the library check.
- **Lock at exact contact:** tap-turn/mirror/refit call the same `find`, so anchors, tie-break (DA-1) and tolerance (DA-3) are unchanged; a refit may move the piece to a neighbouring valid `at` (as the prototype), never to another turn.
- **Preview ≠ drop** is the specific bug the frame-sync rule prevents; do not "optimise" `release` to read the live finger.
- **Reduced motion** is read at event time (solve, pulse) from `ValueAnimator.areAnimatorsEnabled()`, so toggling it while the game runs works on the next event.
- **Open visual choices** (cell colours, tray corner radius, dash lengths): the REQs do not fix them; DI-2 §5 does for pieces/silhouette/paper/tray/accent. Unfixed ones are DA-24, to be judged on the owner's phone.
