### 1. How phones and tablets are verified, and how the device is kept clean *(rev 1: F1, F2, F3, N6)*

**Chosen: a display override on the two AVDs we already have** (`Medium_Phone_API_37.0`, `Phone_API_26`), applied by the test itself, inside a crash-safe frame.

**The override.** `wm size WxH` plus `wm density D` (through `UiAutomation.executeShellCommand`) change the real display, so the real window, insets and rotation follow, on API 26 and API 37. Five exact-dp specs (px = dp × density / 160):

| Spec | dp | `wm density` | `wm size` |
|---|---|---|---|
| `PHONE_390x844` (REQ-035 A1) | 390 × 844 | 400 | 975x2110 |
| `PHONE_360x780` (F9 smallest phone) | 360 × 780 | 400 | 900x1950 |
| `TABLET_1280x800` (REQ-036 A1) | 1280 × 800 | 240 | 1920x1200 |
| `TABLET_800x1280` (REQ-036 A1) | 800 × 1280 | 240 | 1200x1920 |
| `TABLET_600x960` (smallest tablet) | 600 × 960 | 240 | 900x1440 |

The platform clamps a forced display width to twice the initial one (2160 px here), which is why 320 dpi and 2560 × 1600 are not used.

**`DisplayRule(spec)` is an `ExternalResource`, not a `TestWatcher`** (F2: a `TestWatcher` swallows an exception thrown in `starting` and still runs the test). `before()` throws, so a setup failure fails the test; `after()` restores in `finally`. Order inside `before()`:
1. assert the display is **native** (the size and density the AVD was created with; `error("leaked display state from an earlier run")` otherwise, F1b);
2. freeze rotation at 0 (`UiAutomation.setRotation(ROTATION_FREEZE_0)`) after **saving** the prior `accelerometer_rotation` and `user_rotation`;
3. run `wm size` and `wm density`, **draining each command's output to end of stream** (`executeShellCommand` returns before the command is done otherwise);
4. **poll with a timeout** (10 s) until `Resources.getSystem().configuration` shows the expected `smallestScreenWidthDp` **and** `densityDpi`, then until the **real** window size matches. The real size is `Display.getRealMetrics` on API 26–29 and `WindowManager.maximumWindowMetrics` on API 30+, **never `resources.displayMetrics`**, which is the app-usable area (it excludes the navigation bar on API 26, so a correct override would fail). Tolerance 0.5 dp; a mismatch is `error("override not applied: wanted … got …")`.
`after()` runs `wm size reset`, `wm density reset`, restores the **saved prior** rotation settings (never `ROTATION_UNFREEZE`, which would turn auto-rotate on whatever it was), waits for the native display to be observed again (F2: "the restore is observed"), and restores font scale and the other helpers' state through their own `restore()`.

**Crash-safe baseline (F1): `tools/device_reset.py`** (stdlib Python over `adb`; written once, task H-1). It is run by the orchestrator **before and after every device suite** on both channels, because `wm` overrides and the settings below persist across a crashed run, a Gradle timeout and an emulator restart. `python tools/device_reset.py --serial S` resets everything this WO touches to the AVD's native state, then verifies; `--check` only verifies and exits 1 with a list of leftovers:
- display size and density (`wm size reset`, `wm density reset`);
- `font_scale` (1.0);
- rotation: the **per-AVD live baseline** *(orchestrator write-back 2026-10-04, CR-5 N11, DA-108/109: the clean AVDs read `accelerometer_rotation` **1** on both API 37 and API 26, `user_rotation` 0 or unset; rev 2 said "0 and 0", which would have reset a clean device into a different state)*; `font_scale`, `user_rotation` and `airplane_mode_on` read as unset (null) count as the platform default;
- gesture navigation overlay (API 29+): back to the AVD's baseline mode, **a per-AVD constant written in the script** (rev 2, E4), never recorded from a device that may already have leaked: for `Medium_Phone_API_37.0` the mode observed on the clean AVD when H-1 is written; for `Phone_API_26` none (no overlay exists). The "set the mode by hand once" route in the Risks updates this constant;
- airplane mode, **written per API level** (rev 2, E4): API ≥ 30 `cmd connectivity airplane-mode disable`; API 26 `settings put global airplane_mode_on 0` plus `svc wifi enable` and `svc data enable`. `--check` reads the flag on both levels and the radio states on API 26;
- the debug `TestConfig` is process memory only, so it needs no reset.
The older suites (`play`, `browse`, `devtools`, the old `app` tests) do not use `DisplayRule`; they are protected by this script's `--check` **before** they start (so none runs on a leaked 1920 × 1200 display), instead of a `RunListener` in every module (a cheaper way to get the same guarantee, F1c).

**Fallback, written so it can be planned (F2).** If the first device run shows `wm density` disturbing the instrumentation process, the orchestrator sets the display before each Gradle call and runs **one Gradle call per spec per channel**: `python tools/device_reset.py --serial S --display PHONE_390x844` (applies and verifies), then `.\gradlew.bat :app:connectedDebugAndroidTest "-Pandroid.testInstrumentationRunnerArguments.tests_regex=.*\[PHONE_390x844\]" "-Pandroid.testInstrumentationRunnerArguments.displayPreset=true"`, then reset. With `displayPreset=true`, `DisplayRule` only **checks** that the real window matches the spec and throws otherwise. **(rev 2, E2) Rules that make "skips none" true:** (i) every display-dependent class (`PlayThroughAppTest`, `PhoneLayoutAppTest`, `TabletLayoutAppTest`, the held-out touch-target matrix, the language walks that use a display) is `@RunWith(Parameterized::class)` with `@Parameters(name = "{0}")` over `DisplaySpec`: **one spec per case, no loop over displays inside a method**, so a case is named `method[PHONE_390x844]` and `tests_regex` (AndroidX runner 1.7.0, matches `Class#method`; the default `[{index}]` name would select nothing) selects exactly that spec; (ii) every class that uses `DisplayRule` carries one marker annotation, `@UsesDisplayRule`, and a **sixth call** runs everything else on the native display with `-Pandroid.testInstrumentationRunnerArguments.notAnnotation=<package>.UsesDisplayRule`; (iii) **completeness proof:** the executed test counts of the six calls, read from the JUnit XML, add up to the count of the normal full run on that channel; a difference is a failed fallback. Cost: six Gradle invocations per channel, about 2–3 minutes of build overhead each, about 12–18 minutes extra per channel. The seam does not change.

**Rotation** uses `UiAutomation.setRotation(ROTATION_FREEZE_90)` (framework API). On a display landscape by nature (1920 × 1200) a 90° turn gives 800 × 1280 dp, so one flow covers REQ-036 A1's second orientation and A2.

**Every mechanism has a visible scaffolding test before any held-out test uses it (F3).** T-1a ships `HarnessScaffoldingTest` (no token; `// decision DA-96 / DA-98 / DA-99 / DA-102`), one case per helper, each a set, verify and restore: `DisplayRule` (the override applies, the real window is the spec, the restore is observed, and a **mid-process density change leaves the instrumentation alive**); `NavigationMode` (mode 2 reached on API 29+, previous mode restored); `Rotation` (freeze 90 gives the swapped window, the saved prior settings come back); font scale through the debug activity (a `1.3` scale changes a measured text height, no global setting is touched); `AirplaneMode` (flag on then restored, radios restored on API 26); `GestureInsets` (logs the three bottom inserts it read, N5); the locale wrapper (a Finnish launch shows "Kissa" for the Cat); and the visible `PlayerControlWalk` run on `TABLET_600x960`, en, which is the visible signal for L-1 and L-3 (the full touch-target matrix is held-out). **(rev 2, E6a) That walk is its own visible class, `TabletSmallestWalkAppTest` (`// decision DA-99 / DA-100`), outside `HarnessScaffoldingTest` and outside the G-DISPLAY gate, marked "red until L-1" while the 47.78 dp breach stands:** a product breach must not block a harness gate. It must be green after L-1 (or after the sweep withdraws the fix).

**G-DISPLAY gate (rev 1).** `HarnessScaffoldingTest` plus the first `TabletLayoutAppTest` run must pass **on both channels** before the held-out kit copies are compiled against the helpers' behaviour. It proves: (1) `wm` accepts the specs; (2) changing density mid-process does not kill the instrumentation; (3) `smallestScreenWidthDp` follows the override on API 26 and 37 (the F3 portrait lock reads it); (4) every restore is observed; (5) `device_reset.py --check` is clean afterwards. (`TabletSmallestWalkAppTest` is not part of the gate.) If (1)–(3) fail: stop, report, use the fallback. The first API 37 tablet run **records the system UI it shows** (a taskbar or not) in the workorder; whether the override can reproduce a tablet's taskbar is not assumed either way.

The two channels each run the whole `app` device suite; one emulator at a time.

### 2. Phone layout and the gesture bar (REQ-035)

**Code: none** (contingency, N5, below). `TangramApp` pads the screen with `WindowInsets.safeDrawing`, which covers the system bars, the cutout and the IME but **not** the gesture insets; the gesture bar is covered by the navigation-bar inset plus `PlayLayout`'s 10 dp phone bottom margin.

**A1** (`PhoneLayoutAppTest`): on `PHONE_390x844`, with a full-set puzzle seeded through `lastShown` (the fresh-install puzzle is a 3-piece mini): (a) exactly seven tray cells in **two rows** (3 + 4, REQ-035's order); (b) every cell rect inside the `play-area` bounds, the area below the top bar and inside the window; (c) no node on the play screen declares a scroll action (`SemanticsActions.ScrollBy` undefined under the root).

**A2** (`HeldGestureInsetAppTest`), "gesture bar" read as the bottom system area (DA-98): the larger of the stable navigation-bar inset and, on API 29+, the system-gesture and mandatory-gesture insets (from `decorView.rootWindowInsets`: `stableInsetBottom` everywhere, plus `systemGestureInsets` / `mandatorySystemGestureInsets` on API 29+). Every tray cell's bottom, in window coordinates, is at or above `windowHeight − exclusion`. `error()` if the exclusion is 0 on a phone display.
- **API 29+:** gesture navigation is forced first (`Settings.Secure "navigation_mode"`; if not 2, `cmd overlay enable-exclusive --category com.android.internal.systemui.navbar.gestural`; assert it became 2; restore in `after`). **The API 37 run is A2's evidence.**
- **API 26–28** (no gesture navigation exists): the same assertion runs against the visible 3-button bar, and its failure message and report line say **"rule-level: tray above the system bar; REQ-035 A2 not applicable on this API"** (N5). It proves the inset rule, not the criterion.
- **Contingency:** if the API 37 run shows a mandatory-gesture inset larger than bar + 10 dp, that is a real A2 breach; L-3 then adds the bottom `WindowInsets.safeGestures` to the `TangramApp` padding. The test is never loosened.
- Side back-gesture zones are not the gesture bar and are out of scope (risk list).

### 3. Tablet and rotation (REQ-036, REQ-006)

**A1** (`TabletLayoutAppTest`): on `TABLET_1280x800` and `TABLET_800x1280` (full-set puzzle): seven cells, **one row** (all tops equal within 0.5 px, lefts strictly increasing in REQ-036's order), all inside the play area. A decision test adds `TABLET_600x960`.

**A2, rotation, no code change.** The state is the `PlaySession` in `AppViewModel.host`; the activity declares no `configChanges`, so a rotation recreates the activity while the ViewModel, with the session, controller, grid flag and aid state, survives (DA-26, F3). `onPause` interrupts a drag and saves (DA-49), and a rebuilt composition seeds its clock from the session's last frame time (CR-F1), so glides and the solve timeline continue. **No `SavedStateHandle`, no new field, no format change: LOCK-V1 holds.**
- `HeldRotationAppTest`: on `TABLET_1280x800`, seed a full puzzle, place two or three pieces by real touch on their solution places (the `TouchRig` helper), record each solution-polygon centroid in puzzle units, `setRotation(ROTATION_FREEZE_90)`, wait idle, assert 800 × 1280 dp, `puzzle-state` still "in progress", and **each piece's colour at its centroid mapped through the *new* `BoardTransform`** (DA-40/DA-70: the public transform, a centroid, never a corner), and the other pieces' tray cells still present.
- Decision tests (`// decision F3`, no token): an open grid survives the rotation; a rotation **during** the solve timeline keeps the solved state (N9).

### 4. Touch targets (REQ-037) *(rev 1: F4, N4)*

**What counts as a "player control" (DA-99).** A node of the **merged semantics tree** with a click or long-click action or an interactive role, classified by its own test tag, else by the nearest tagged ancestor (the grid cell's click layer is untagged under the tagged cell); an interactive node with **no** tagged ancestor fails the walk; plus the **flip badge** (`flip-badge`) and the **seven tray cells** (`BoardTransform.trayCellsPx`, "a tray piece's touch area is its whole cell"). **Not** controls: the board, board pieces (REQ-015's 12 dp reach owns them), text, rating dots, size marks. **Skipped:** any node whose tag, or nearest tagged ancestor's tag, starts with `dev-`, and the Restart pill while hidden.

**The walk** (`PlayerControlWalk`; the full matrix is held-out in `HeldTouchTargetAppTest`; a one-display run is visible in `HarnessScaffoldingTest`; WO-007/008 reuse it):
- Screens: New, In progress (Restart visible), Solved (a seeded stored Solved entry), grid open (scrolled to **every** puzzle index, since the grid is lazy: one cell per library puzzle).
- **REQ-037 is tested at the REQ-006/035/036 reference windows** (rev 1, F4): `PHONE_390x844`, `TABLET_1280x800`, `TABLET_800x1280`, plus `PHONE_360x780` (F9, REQ-013 A1's size), `TABLET_600x960` (the smallest tablet) and the AVD's own size. Languages: en everywhere, fi on `PHONE_360x780` and `TABLET_600x960`. Font scale 2.0 on `PHONE_360x780` only, for "a size in dp does not shrink with the font" (the scale comes from the debug seam, section 5).
- Every control: width ≥ 48 and height ≥ 48 dp, each axis separately; `prev-button`, `next-button` ≥ 52; `flip-badge` ≥ 60 (REQ-037's rules, guardrails, no token).
- **The walk is not blind:** per screen it must find the controls that must exist (play: prev, next, counter, seven tray cells for a full puzzle; In-progress adds Restart; Solved adds Retry and Next; grid adds Done and one cell per library puzzle), or it fails "walk blind".

**The tablet finding and its fix (DA-100).** From REQ-013's rule values (padding 12, diameters LT 4.22, PG 3.16, MT 2.98, ST 2.11, SQ 2.00) and `PlayLayout`'s constants, the square's cell is `2.00 × ts + 12`. The reviewer re-derived it with exact diameters:

| Window (dp) | smallest cell now (SQ) | after tablet gap 14 → 12 |
|---|---|---|
| tablet 600–602 wide | **47.78** (603 gives 48.07) | 49.32 at 600 |
| tablet 800 × 1280 | 67.0 | 68.56 |
| tablet 1280 × 800 | 67.02 (height-limited) | unchanged |
| phone 360 × 780 / 390 × 844 | 60.3 / 65.6 | unchanged (phone gap stays 8) |
| any window **shorter than 549.3 dp** | below 48 (the row cap, 46.2 at 525 and below, REQ-013) | unchanged |

- **Fix, tablets (stays):** the tablet `gap` in `PlayLayout` goes 14 → 12 dp. Gap counts (n + 1) = 8 times in `trayScaleFor` and the side margin twice, so the gap frees 16 dp (49.32) where the margin 16 → 12 would free only 8 dp (48.55); that is why the gap is the lever (rev 1, N4: row corrected). The 1280 × 800 tablet is height-limited and does not change. **This departs from `Spec/02-ui-layout.md` §3.4 and the prototype (`tools/prototype_template.html`, the same (n + 1)-gap formula)**; both are explanatory inputs (DI-1/DI-2), not Contract. The departure is added to `design-inputs.md` §2 at the close (AGENTS rule 9 says the REQs win and the template is fixed; the capture side is told in CA-7(c)). It is confirmed first by the sweep; **if the sweep does not show the breach, the fix is dropped.**
- **Short windows: a conflict between two locked REQs, not "unsupported" (DA-100, rev 1, F4).** Below **549.3 dp** of window height, REQ-013's own rule (a row is at most `max(84 dp, 16 % of H)`, padding 12) makes the square's cell 46.2 dp, below REQ-037's 48 dp. No build value satisfies both. Decisions F3 names split screen as a window change the game re-lays for, and F9 bounds only the width, so such windows are real. **Interim rule: REQ-013's cap holds (today's behaviour)**; in a window under about 549 dp tall (split screen is the case) the square's tray cell may be under 48 dp. This is a **known interim**, shown to Jami as a REQ conflict at the checkpoint. **No code for either way out in WO-006.** CA-7(b) is a two-option CHG for Jami: (i) the 48 dp floor wins, so rows may exceed REQ-013's cap below that height; or (ii) REQ-037 names a supported window.
- `TraySizeSweepTest` (`play/src/test`, no token, `// decision DA-100`): every width 360–1400 in 10 dp steps × heights **560**, 640, 780, 844, 960, 1200 (the sweep stays clear of the 549.3 boundary: 550 passed by only 0.05 dp), for the class the width selects, the 7 full-set pieces: smallest cell ≥ 48 dp both axes, 2 rows (phone) or 1 (tablet), all cells inside the area. A second, **non-asserting** case prints the smallest cell for heights 500–549 in 10 dp steps, so the conflict is on record with numbers.

### 5. Language (REQ-047) *(rev 1: F5, F7, N3)*

**Who chooses the language.** Android chooses the resources: `values-fi/` for Finnish, `values/` (English) for everything else, in every module (G-05). **No in-game switch.** The app adds **titles from the library**, `title[lang]`, read today from `LocalConfiguration.current.locales[0].language` (`BrowseTopBar`, `AllPuzzlesOverlay`).

**What the real APK does (reviewer, from the merged release resources).** The merged APK carries androidx/Compose translations in 85 `values-*` folders, **`values-sv` among them**. For a *Swedish, Finnish* list Android resolves the resources to `sv`; our modules have no `sv`, so every string falls back to English, and `locales[0]` is `sv`, so the title is English too: **one language, consistently English**. Where the resolver does pick a later list entry it moves that entry to the front of the configuration's `LocaleList`, so `locales[0]` very likely already *is* the resolved language. So the rev 0 defect ("Finnish buttons over an English title") is **not shown to exist**.

**Decision (DA-101, rewritten): no behaviour change; test first.** The mixed-list case is a **visible decision test, run on today's code before anything is changed** (it is in the first device run): three lists, each must give one language across the screen (the title language equals the Restart label language) and the test records which: `sv-SE,fi-FI` (resolves to `sv`, so English), the control `fi-FI,sv-SE` (Finnish), and **(rev 2, E1) `se-NO,fi-FI`**: Northern Sami is packaged by no library (none of the 85 `values-*` folders is `se`, `smn` or `fo`) and Finnish users really set it, so it is the only kind of first entry for which Android resolves *past* it to `fi`. Expected: every string Finnish; the title is Finnish only if the platform moves the resolved locale to `locales[0]`. **`se-NO,fi-FI` is the case that decides the L-2 contingency**: neither of the other two lists can ever show titles in another language than the buttons. **L-2 (`ui_language`) is dropped.** It returns only as a contingency, with the smallest fix (the `ui_language` string read by the two title call sites), if the test shows titles in a different language than the buttons. The owner option (CA-8(a), owner item 2): *with `androidResources { localeFilters += listOf("en", "fi") }` in the app's `build.gradle.kts` (the AGP setting that drops the libraries' other translations), a Swedish, Finnish list would show Finnish; today it shows English.* REQ-047's "device language" (Finnish when the language **is** Finnish) and decisions F6 ("the language Android reports for the app") do not decide it; WO-006 does **not** add `localeFilters`.

**"Kissa" is served by the library:** `Tangrams/animals-cat.json` has `title.fi = "Kissa"`. REQ-047 A1's puzzle part is an on-screen assertion: top bar and grid cell description in Finnish ("Kissa" literal, the REQ's own text); English from the library otherwise.

**How a device test switches the locale and the font scale on both channels (DA-102, rev 1).**
- `MainActivity` becomes `open` (the only product change in `app/src/main`; behaviour identical).

A debug manifest (`app/src/debug/AndroidManifest.xml`) declares the activity (`exported="false"`). Tests launch it with `ActivityScenario.launch(LocaleOverrideActivity::class.java)`, so the **real `MainActivity` code runs**. **The font scale is set per launch, never as the global `font_scale` setting** (F7, F1d): nothing leaks. `TestConfig` is reset to nulls by the tests' `after`; `Resources.getSystem()` (the F3 orientation rule) is untouched.

- **The tablet 600 dp finding is arithmetic until the sweep runs;** it uses the real `TrayRules` and `PlayLayout`, so the sweep is the authority. If it does not show the breach, the fix is dropped.
- **REQ-013 ↔ REQ-037 in short windows** is a known interim, not a pass (DA-100, CA-7(b), owner item 1). Split screen on a small phone is the case. No code in WO-006.
- **Locale switching on API 26.** The wrapper is the one mechanism for both channels; the first device run shows `LocalConfiguration` and `stringResource` follow it (fallback `applyOverrideConfiguration`).
- **REQ-035 A2.** Before API 29 the criterion does not apply and only the rule is tested (stated in the report line). On API 37 the gesture inset may exceed bar + 10 dp; the contingency is `safeGestures` in L-3. A piece dragged to the screen edge can start the system Back gesture: a feel question for the playtest.
- **Gesture mode on the emulator.** `cmd overlay` needs API 29+; if the shell identity is refused, the test fails (never skips) and the orchestrator sets the mode once by hand (it persists; `device_reset.py` records and restores the AVD's default).
- **The Finnish solved bar at 360 dp, 1.0** may already clip; the walk checks it; L-3 is the contingency.
- **Rotation state.** Safe by construction; a drag in flight is returned silently (F5); the 16 MB picture cache is rebuilt on a layout change (DA-42).
- **Airplane mode on API 26** is "flag set, radios off" (root needed for the real toggle); the argument carries the claim (DA-105).
- **V-08 builds the release APK itself** (an up-to-date Gradle build after V-04 is quick); a hit on an SDK class definition is a G-01 breach and a stop.
- **The walks must not be blind.** Each has a "must find" list; the held-out copies are separate.
- **Release safety.** `LocaleOverrideActivity` and `TestConfig` are debug-only; V-08 denies their class definitions in release and requires them in the debug APK (`--expect-debug`); `open` changes an access flag only; V-01 and V-04 stay green. The scan inputs in `app/build.gradle.kts` use globs and never the word "devtools" (DA-89).

The touch-walk matrix is trimmed: 4 screens × 6 displays in en (24 launches), fi on two displays (8), font 2.0 on one phone (4): about 36 launches per channel instead of 72. If the real figure doubles, trim the grid scroll first.
- **The v1 save format.** Unchanged. Tests seed stored states through the existing store only.
