# Design — WO-009 · #Release: the first-release library, the release gate, the store-bound artifact and the release checklist

**Author:** Design Author  ·  **Date:** 2026-10-05  ·  **Rev 0**  ·  **Baseline:** architecture.md v1.0 (G-01, G-02, G-03, G-04, G-06, G-08, G-09, §5 test placement, ADR-004/005/006), build-map v1.7, decisions.md (to DA-152; F9, F14, F16, F17, F18, DA-88/89, DA-104, DA-126, DA-133…152), governance rows 8, 10, 11, 12, 13, 14, 15, 16, 17, 18, REQ-048, 042, 039, 001, 010, 049, 009, `req_review_01.md` (F17, F34, F37), `Requirements/requirements.md` §5, `Tangrams/README.md`, `Spec/03-puzzle-format.md`, the content pipeline (`tools/validate_puzzles.py`, `render_puzzle.py`, `export_geometry_golden.py`, `check_apk_puzzles.py`, `content/build.gradle.kts`), the verifiers V-01, V-04, V-08 and `trace_check.py` (read only), `designs/WO-008-design.md` (form).

**In one paragraph.** WO-009 needs **no product code**. Everything the locked REQs ask of #Release is content, evidence or release plumbing. (1) **Library:** the build side **drafts 10 new full puzzles** through the existing pipeline (13 → 23; five themes today, six after; `shapes-square` stays) with `reviewedByHuman: false`; the choice of figures and the count are taste and go to the owner as a veto, but authority over the flag stays with Jami. (2) **Review:** the AI prepares a generated review sheet; **Jami records his approval by running one interactive command himself** (`tools/puzzle_review.py mark`), which flips the flag, writes a **review ledger** (`release/puzzle-review.json`: the content hash he approved) and refreshes the golden. The AI never sets the flag and never runs `mark`. (3) **Gate:** a new release-time verifier **V-09** reads the release artifact (or `Tangrams/`) and fails on any unreviewed puzzle, any stale approval (the file changed after the ledger hash), fewer than 20, fewer than four themes or a missing `shapes-square`. It is **not** part of `gradlew test` or any debug path, so debug builds and tests are untouched while no puzzle is reviewed; it is **RED by design until Jami reviews**, and the WO closes "release-ready, waiting for Jami". (4) **Artifact:** the store-bound artifact is the release bundle's universal APK if the channel is Play (the signed APK otherwise); V-01, V-04, V-08 (permissions, SDK classes, feedback callers), V-09 and the API 26 release launch with a `dumpsys` permission line run on it (C8). **No signing configuration enters the repo** (security floor). (5) **Listing:** the AI drafts the listing text (EN and FI), the hosted privacy text, the Console declaration answers and a **release checklist**; JVM tests tie the drafts to the REQ strings and to the in-app privacy text; **each manual item is a row with its REQ token and an owner**, and the tokens that trace-check can count sit on the draft and gate tests, with their evidence limits stated. The channel, the account, the key, the declarations and the publish are Jami's.

### 1. Module and code-home shape

No new module, no new dependency (row 15: none), no `src/main` file. The #Release row of `build-map.md` keeps code home `—` (system-level, checked at app and release level). **trace-check rule 3** binds the content REQs: REQ-042 (feature `PuzzleVolume`) and REQ-039 (`PuzzleArt`) inherit code home `content`, so their covering tests live in `content/src/test`. REQ-048 and REQ-001 map to no code home, so their tests may sit in `app`. The build edits are two small lines in two files, done by one task that runs alone first (the DA-126 form): `content/build.gradle.kts` (the `releaseGate` property into the test task's system properties, and `release/puzzle-review.json` is **not** a content-test input) and `app/build.gradle.kts` (`"release/*"` added to `scannedFileGlobs`, so the new JVM tests re-run when a draft changes: the DA-88 input rule); plus `.gitignore`.

**How they are made (the existing pipeline, per puzzle, AGENTS rules 7 and 10).** (1) Write the file with the **Write tool** (never a Python literal that writes a project file, the backslash lesson); `provenance: {"author": "ai:claude", "reviewedByHuman": false}`. (2) `python tools/validate_puzzles.py Tangrams` (V1–V6, V8–V10, V12; V11 prints the build order and never fails a valid puzzle, rule 6). (3) `python tools/render_puzzle.py Tangrams Tangrams/previews`, then `svg2png.py`, and **look at the sheet** (silhouette | pieces | picture): is the silhouette recognisable without inner lines, is the picture flat, 3–8 colours, no text, inside the outline (REQ-039 rule). (4) After the batch: `python tools/export_geometry_golden.py` (G-03; it refuses a validator error), `python tools/build_prototype.py`, `python tools/tests/test_prototype.py`, `Requirements` `validate.py` (rule 10). (5) The content module packages `Tangrams/*.json` by itself (`packagePuzzles`, G-08): **no build change for the new files**; `tangrams/index.txt` is regenerated; `check_apk_puzzles.py` (inside V-04) then proves the APK holds exactly the repo's files.

**Ripples, named (the WO-008 B1 lesson).** The plan runs a grep before authoring, as in WO-008, for tests that enumerate the library: `PlaceSecondarySweepTest` and `TimerPlacementSweepTest` sweep every puzzle (they only assert `>= 13`), `LibraryOnDeviceTest` (count = index lines), the grid tests (`grid-cell-<id>`: 23 cells may need a scroll the 13-cell tests never made), `FreshInstallScreenTest`, `BrowsingAppTest`. **A sweep that goes red on a new silhouette is a product finding to route, never a test to loosen** (the DA-150 N1 count, 256 of 2340 layouts touching an outline corner, will change; the new count goes to checkpoint 9). Titles pass `PromiseSourceScanTest`'s Finnish and English word lists (it scans `Tangrams/*.json`); `UntranslatedStringsTest` is not touched (no string resource is added).

**Staffing.** Puzzle authoring is creative and visual: slice-implementer with a **sonnet** override, three batches (animals + people, things + vehicles, nature), each ending in steps 2 to 4. The orchestrator reads each preview sheet before accepting a batch. A "complete" file that only validates but whose silhouette is unreadable is a rejected hand-back.

### 3. How Jami's review is prepared and recorded *(REQ-039 rule, REQ-042 A1; fork 3)*

**What the AI prepares.** `python tools/puzzle_review.py sheet` writes **`reviews/WO-009-puzzle-review.md`** (generated, rule 8: edit the generator): the 23 puzzles in game order with id, both titles, theme, kind, rating, validator verdict, colour count (information), the preview image link, and the ledger status (waiting, reviewed, or **STALE**); at the top, the exact steps: install `app/build/outputs/apk/debug/app-debug.apk`, solve each puzzle by hand (the DEV pill, passcode 0417, shows the solution when stuck), check the silhouette and the picture, then record. The orchestrator hands him this build at the checkpoint ("a build to try", governance row 17).

**How it is recorded: the flag plus a ledger, written by one command he runs.** `python tools/puzzle_review.py mark <id> [<id> ...]` **refuses to run unless stdin and stdout are a terminal** (an agent's shell is not one), shows each title and asks him to type `APPROVED`, then for each puzzle: flips `"reviewedByHuman": false` to `true` in that file (text edit, formatting kept), writes `{sha256, date, by}` for it into `release/puzzle-review.json`, and finally runs the golden exporter (the file's hash changed, so without it the next `gradlew test` is red: a trap he should not meet). `sha256` is `review_hash(text)`: the file with CRLF as LF and the flag normalised to `false`, so it is the hash of **what he approved**, independent of the flag.

**Stale approvals.** If a reviewed file is edited afterwards (a picture touch-up), its `review_hash` no longer equals the ledger's and V-09 prints **STALE**: the approval was for other content. **The rule for the AI: an edit that changes a reviewed puzzle sets its flag back to `false` in the same edit** (safe direction; the AI may do that, never the other way). The new lesson goes into AGENTS.md and the handoff.

**Honest limit.** This catches accidents (a stale approval, a flag flipped in passing, a forgotten file). It does not prove who ran a command, and a deliberate forgery by an agent is not stopped by a TTY check: that is what AGENTS rule 7, the floor and his own eyes are for. The design says so rather than claiming a security control.

**The AI's tests of the tool** run `mark`'s function on a temporary copy of fixture files (never `Tangrams/`), never the CLI.

### 4. The release gate: V-09, and how it coexists with debug builds and tests *(REQ-039 A2, REQ-042 A1; question 2)*

**`.swdev/verifiers/v09_release_library.py`**, stdlib, with self-tests in `test_verifiers.py` (each failure mode has a fixture that fails). Input: `--dir Tangrams` (default) or `--apk <the store-bound apk>` (reads its `tangrams/*.json`, so it checks **what ships**, byte-equal to the repo files by V-04's `check_apk_puzzles`), `--ledger release/puzzle-review.json`, `--min 20`. Output lines in the V-04/V-08 style: `V-09 FAIL unreviewed <id>`, `V-09 FAIL stale <id>` (hash differs from the ledger), `V-09 FAIL unledgered <id>` (flag true, no ledger entry: someone set the flag without `mark`), `V-09 FAIL count R of N reviewed (< 20)`, `V-09 FAIL themes C (< 4)`, `V-09 FAIL missing shapes-square`, a warning for ledger entries with no file, and one summary line `V-09 library: R of N reviewed, C themes`. Exit 0 pass, 1 findings, 2 cannot read (a file that does not parse, a missing ledger when any flag is true). "True" means the JSON literal `true` only, as the parser reads it (`reviewedByHuman` as a string `"true"` is a finding).

**Coexistence.** V-09 is a script run at release time. It is **not a Gradle task, not part of `assembleDebug test`, not part of V-04 or V-08**, so debug builds, the JVM tests and every device suite are unaffected while no puzzle is reviewed. Today it prints `0 of 13 reviewed` and exits 1. That is the expected state and is recorded as such at the close; **it is the one verifier whose RED is by design**, and the close report shows its line verbatim next to the other verifier lines (so a green trace-check is never read as "ready to publish").

**JVM level (`content/src/test/.../release/ReleaseLibraryTest`).**
- `REQ-042.A2` and `REQ-042.A3`: over the real library from `tangram.root`, always on: at least four distinct categories; `shapes-square` present. Full meaning, both green today.
- `REQ-042.A1` and `REQ-039.A2`: a small test-side rule (`reviewed >= 20`; no puzzle unreviewed) is proven on fixture lists (20 reviewed passes; 19 fails; 20 reviewed plus one unreviewed fails the REQ-039 case). The **real library** is asserted by the same rule only when `-PreleaseGate=true` is passed (`.\gradlew.bat :content:test -PreleaseGate=true`, a system property through `content/build.gradle.kts`); without it the test prints one line `release gate NOT enforced: R of N reviewed` and passes. The meaning of the token is "the rule decides as the REQ says"; the data verdict is the gate run, which is why the checklist's command list has both V-09 and the `-PreleaseGate` run (V-09 reads files and the ledger; the Gradle run proves the **parser's** reading of the flag, which is what the app sees). The two implementations check different inputs; the Python one is the shipping gate. Evidence limit, written in the test header and DA-156.

### 5. The store-bound artifact and its checks *(REQ-048 A3, REQ-010 A2 C8, REQ-001; question 4)*

- **Which artifact.** Channel-neutral core: `:app:assembleRelease` gives the unsigned release APK that V-01, V-04 and V-08 already run on at every close. **If the channel is Play (recommended interim)** the store-bound artifact is the release **bundle**: `:app:bundleRelease`, and to scan what Play will split from it **`:app:packageReleaseUniversalApk`** (an AGP task that builds a universal APK from the bundle; assumed available in AGP 9.4.1, **a spike in the plan confirms it**; if it is not, the fallback is that the bundle is built from the same merged manifest V-01 checks and the checklist asks Jami to run his own bundle tooling, which the design then lists as an unproven link, not green). V-04 and V-08 already take `--apk`; they run on the universal APK: no SDK class definitions, no permission element, the DevTools markers absent, the feedback-caller allow-list unchanged, and `tangrams/` equal to the repo's. V-09 runs on the same APK. For F-Droid or a signed APK the APK is the artifact and nothing else is needed.
- **REQ-048 A3 and C8.** Token carrier: a **new visible** device test `app/src/androidTest/.../release/ReleaseInstalledPermissionsAppTest` (`REQ-048.A3`), reading `targetContext.packageName`, the same query as the held REQ-010 test, with the control that the platform package declares permissions. It runs on the debug build (instrumentation needs it), so the **store-bound proof** is: the three verifiers on the release artifact plus the throwaway-signed copy launched on **API 26** with `dumpsys package <pkg>` showing an empty `requested permissions` section and 0 FATAL lines (the WO-005/008 procedure); both lines are recorded in the checklist and the workorder. REQ-010 A2's token stays on `HeldInstalledPermissionsAppTest` (C8 re-verified with the same token, no copy of it).
- **Signing (fork 5, floor F2).** Gradle emits only unsigned artifacts. No `signingConfig`, no key, no password, no property that points at one, anywhere in the repository. `.gitignore` gains `*.jks`, `*.keystore`, `keystore.properties` as a guard against an accident. The throwaway-signed API 26 copy is made in the scratchpad with the local **debug** key, never committed, as in every WO since WO-005.
- **Version.** `versionCode = 1`, `versionName = "0.1.0"` are left alone (fork 10).

### 6. The listing, the privacy text, the Console answers, the checklist *(REQ-048 A1–A2, REQ-001 A2, C11; question 3)*

**What the AI drafts (all under `release/`, plain Markdown, EN and FI):**

Each Console rule is marked "verify against the Console's current wording".
- **`privacy-policy.md`:** the REQ-049 sentence verbatim in English and Finnish (taken from the in-app strings), nothing more; with the `TBD-OWNER` URL slot in the listing until fork 4 is decided.
- **`release-checklist.md`:** one row per item with columns `id` (the REQ token or a name), `item`, `kind` (machine or manual), `command or action`, `owner` (`ai` or `jami`), `status` (`waiting-for-owner`, `done`, `n/a (channel)`), `evidence`. Machine rows: trace-check; V-01; V-04 and its positive control; V-08 and `--expect-debug`; V-09; `-PreleaseGate`; the API 26 release launch and `dumpsys` line; `bundleRelease` plus the universal-APK scans. **How trace-check sees the tokens (answering F17's "their tokens are covered there").** `trace_check.py` counts a token only in files matching `guard.json` `test_globs` (`*/src/test/*`, `*/src/androidTest/*`) as the text `REQ-NNN.An`; a Markdown checklist is invisible to it. So the checklist carries each token **for the reader**, and the **tokens that count** sit on JVM tests that assert what the build side can assert, each under its code home and each stating its evidence limit:

| ID | What the carrying test asserts (the REQ's meaning, as far as a test can) | Evidence limit (the rest is Jami's row) |

## Risks & edge notes

- **Highest risk, for the Design Reviewer's spot-check: green tokens that can be read as "ready to publish".** REQ-042 A1 and REQ-039 A2 are green in trace-check on a rule test while **0 of 23 puzzles are reviewed**; REQ-048 A1/A2 and REQ-001 A2 are green on **drafts**. The design contains it by (a) evidence limits written in each test header and in section 6, (b) V-09's RED line and the unchecked manual rows printed in the close report next to the verifier lines, (c) the WO closing "release-ready, waiting for Jami", not "released", and (d) DA-156 saying so. A reviewer should challenge whether the token placement is honest enough, whether the rule test's `-PreleaseGate` mode earns `REQ-042.A1`, and whether the close report wording cannot be misread. Second-order target: `mark`'s TTY check and the ledger (section 3): a speed bump against accidents, **not** a control against an agent that wants to forge; named as such.
- **New silhouettes feed every all-puzzle sweep and walk.** The timer-placement and secondary-control sweeps, the grid tests (23 cells), first-launch and promise walks may expose a layout fault only a new shape has. Route as product findings (never loosen); the DA-150 N1 count changes and goes to checkpoint 9. Prototype tests and the golden regenerate with every batch.
- **Recognisable figures are hard to author exactly.** The validator proves geometry, not that a "rabbit" reads as one. Mitigation: render, look, iterate; the owner's review is the real check; ratings and figures are his to veto. A near-duplicate silhouette is not detected by any tool (listed, not built, D2).
- **The golden and the ledger are hash-bound to the file bytes.** Every approval changes a file, so the golden must be re-exported (done by `mark`), and every later AI edit must set the flag back to `false` (the new rule). A forgotten re-export is a red `gradlew test` with the exporter's own hint, never silent.
- **The universal-APK task is an assumption** (`packageReleaseUniversalApk` in AGP 9.4.1); the spike is the first task of the artifact work. If it fails, the Play bundle's permission proof rests on the shared merged manifest plus Jami's own tooling, and the checklist says so (not green).
- **Google Play facts change** (the closed-test rule, the Families wording, store field limits 30/80/4000, the questionnaire). The draft marks each "verify in the Console"; none is encoded as a test except the field lengths.
- **Hosted policy needs a public repo (F34).** Fork 4. Until decided the URL is `TBD-OWNER` and the checklist row stays waiting.
- **The Finnish is AI-written** (puzzle titles, the Finnish listing). Owner list; the store title stays a draft until he confirms.
- **Release safety at the close:** nothing in `src/main` changes, so V-04, V-08 and the caller allow-list are re-run, not re-judged; `--positive-control` is re-run after any toolchain or dex change (none expected). One Gradle build at a time; `tools/device_reset.py` before and after every device step; API 37 and API 26 suites, the display gate first.
- **Size of the owner's job:** 23 puzzles to solve and judge. Stated up front in the review sheet and at the checkpoint so it is a known evening, not a surprise.
