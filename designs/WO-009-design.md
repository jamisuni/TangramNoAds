**The picture rule, checked mechanically (S3, DA-162; the visible-colour reading, rev 2).** REQ-039's rule is "flat shapes, 3–8 colours and no text". **The count** is the number of distinct **visible** colours: the distinct normalised `#RRGGBB` values over `art.base` and every shape's `fill` and `stroke`, where a shape drawn at an opacity below 1 adds one visible colour per distinct (hex, opacity) pair (a tint over the base is a colour the player sees); the range is 3 to 8 inclusive. The alternative reading (a tint counts as its own hex, so white at 0.35 is white) is not chosen: it would force edits to the minis and warm-ups the owner has already played. "No text" holds by the format: no art shape type draws text (schema and V10). New rule **V14** in `tools/validate_puzzles.py` (a failing check; `Spec/03` rule table and `Tangrams/README.md` updated; the golden exporter already fails on a validator error). **Before the review sheet exists**, the existing files are brought into the rule: only `things-house` (11 hex values) fails under both readings; the V14 run decides, the implementer edits only `art` (never `solution`), and the change list goes to the owner **with before and after previews of every changed picture**: "these pictures changed since the build you last played". Fixing is an AI decision (row 12, with CA-13), not an owner stop: all 13 are unreviewed AI drafts and the edit conforms to a locked rule. Done now it costs nothing; after the review it would cost a second review.

**How they are made (per puzzle, AGENTS rules 7 and 10).** (1) Write the file with the **Write tool** (no Python literal that writes a project file). `provenance: {"author": "ai:claude", "reviewedByHuman": false}`. (2) `python tools/validate_puzzles.py Tangrams` (V1–V6, V8–V10, V12–V14; V11 prints the build order and never fails a valid puzzle, rule 6). (3) `python tools/render_puzzle.py Tangrams Tangrams/previews`, `svg2png.py`, and **look at the sheet** (silhouette | pieces | picture): is the silhouette recognisable, the picture flat. (4) After the batch: `python tools/export_geometry_golden.py`, `build_prototype.py`, `tools/tests/test_prototype.py`, the Requirements `validate.py`. (5) `packagePuzzles` packages the files by itself (G-08); no Gradle change.

### 3. How the owner's review is prepared and recorded *(REQ-039 rule, REQ-042 A1)*

**The sheet (generated, bound to the played build, rev 1 S4b, N7).** After the last batch the orchestrator builds the debug APK, then runs `python tools/puzzle_review.py sheet --apk <that apk>`. It reads `tangrams/*.json` **from the APK** and refuses if they differ from `Tangrams/` ("stale build, rebuild"). It writes `release/puzzle-review-sheet.md` and `.json` (a generated file; the orchestrator adds it to AGENTS rule 8's list at the close): the 25 puzzles in game order with id, both titles, theme, kind, rating, validator verdict, colour count, preview link, **the puzzle's `review_hash`**, the APK's sha256, the ledger status (waiting, reviewed, **STALE**), and an empty **approve / fix / reject** column. The top says: install that APK; solve each puzzle by hand (the DEV solution overlay is a fine hint; **the DEV "Solve this puzzle now" aid does not count as solving**, REQ-039 rule); check the silhouette and the picture; run `mark` in **PowerShell or cmd** (Git Bash reports no terminal and is refused).

**Recording: the flag plus a ledger, written by one command the owner runs.** `python tools/puzzle_review.py mark <id> [<id> ...]` refuses unless stdin and stdout are a terminal (and says why), shows each title, and asks for `APPROVED`. For each puzzle it **refuses if the file's current `review_hash` differs from the sheet's** ("changed since the build you played: rebuild, regenerate the sheet, replay"), otherwise flips `"reviewedByHuman": false` to `true` (text edit, formatting kept, inline and multi-line forms), writes `{sha256, date, by}` to `release/puzzle-review.json`, and finally runs the golden exporter (the file's hash changed; without it the next `gradlew test` is red). `review_hash(text)` is the file with CRLF as LF and the flag normalised to `false`: the hash of **what was approved**, independent of the flag.

**Stale approvals and re-approval (S4a, c).** If an approved file changes, V-09 reports **`changed after approval <id> (approved <date>)`** and the owner can re-approve it: `mark` accepts a file whose flag is already `true` but whose hash differs from the ledger ("content changed since your approval on <date>; type APPROVED to approve the new content"), subject to the same sheet-hash check. **The AI does not edit an approved puzzle unless the owner asks for the edit.** When asked, the AI resets the flag to `false` in that same edit and logs it; V-09 then reports `unreviewed <id> (was approved <date>, content changed)`, keeping the history. G-08's literal text ("Agents never set `reviewedByHuman`") is read as never setting it to `true`; an owner-requested reset to `false` is a revocation, logged under row 13 (`ai+inform`, DA-156).

**The reject / fix path (S5; rev 2: none of it runs on release day).** The owner marks each puzzle approve, fix or reject in the sheet and tells the AI. **Fix:** the AI edits the file on the owner's word, the sheet is regenerated from a fresh debug build, the owner replays that puzzle. **Reject:** the AI **removes the file from `Tangrams/` on the owner's word** (ids never reused; G-08: the release library is `Tangrams/`, no filtering). A removal changes the library after the evidence, so it runs in the pre-publish phase of RELEASE-DAY **before** the rebuild, with a named re-run list: the golden export, `gradlew.bat assembleDebug test`, V-04 (its `tangrams/` check), V-09, and a device smoke on both channels (at least `LibraryOnDeviceTest` and the first-launch test). **If a mini or warm-up is rejected**, REQ-040/041/045 still need a rating-1 mini first and warm-ups next: with `shapes-mini-1` gone the tests that name it (`ContractAndDecisionTest`, kernel and play fixtures, the held first-launch class) need **corrected checks by the Test Author** pointing at the next mini. That, every fix and a late icon are **not mechanical, so they never run inside RELEASE-DAY: they go to a short follow-up WO** (its own review station); a rejection of the last mini or of all warm-ups is a **fix**, not a removal.

**Honest limit.** The TTY check and the ledger catch accidents (a stale approval, a flag flipped in passing, a forgotten file, a build that differs from what was played). They do not prove who ran a command; a deliberate forgery by an agent is not stopped (`Bash(python:*)` is allowed and `mark_files` is importable). Cheap guards: `mark_files` **refuses the repository's own `Tangrams/` unless called through the CLI's confirmed path** (a Python test asserts the refusal); the optional `deny` rule is offered to the owner; the ledger is **not** put in `guard.json` (every `mark` would show as contract drift). AGENTS rule 7, the owner floor and the owner's attention are the real control. The AI's tests run `mark_files` only on temporary fixture copies, never on `Tangrams/`.

### 5. The store-bound artifact and its checks *(REQ-048 A3, REQ-010 A2 C8, REQ-001)*
